# FT-006: 结构化修复指令

## 基本信息
- **Feature ID**: FT-006
- **功能名称**: 结构化修复指令
- **对应需求**: REQ-010
- **功能类型**: 决策机制
- **优先级**: 必须
- **状态**: 待实现

## D-01: 功能标识
- **Feature ID**: FT-006
- **入口类型**: Output Format
- **入口路径**: 审查报告中的修复指令部分

## D-02: 输入规格
| 参数名 | 类型 | 必填 | 约束 |
|--------|------|------|------|
| finding_id | string | 是 | 问题编号 |
| target_doc | string | 是 | 目标文档路径 |
| fix_action | string | 是 | 修复动作描述 |
| evidence | array | 是 | 证据摘要 |

## D-03: 前置条件
- Finding 已通过 AUTO-FIX 决策

## D-04: 正常输出
```yaml
fix_instruction:
  finding_id: string
  target_doc: string
  fix_action: string
  evidence_summary: array
  verification: string
```

## D-17: Test Oracle
**业务规则**:
- 必须包含至少 2 个证据维度
- 可被编排器机器解析

## D-19: Test Case Groups
| 测试组 | 用例数 | 优先级 |
|--------|--------|--------|
| 格式验证 | 3 | P0 |
| 解析测试 | 2 | P0 |

## D-20: Coverage Claim
- **格式覆盖**: 100%

## D-05: 异常行为
| 错误码 | 触发条件 | 行为 |
|--------|---------|------|
| ERR-FIX-001 | Finding ID 无效 | 跳过该指令，记录警告 |
| ERR-FIX-002 | 证据维度 < 2 | 降级为 ASK |

## D-06: 边界值
- 证据维度 = 0 → 禁止生成 AUTO-FIX 指令
- 证据维度 = 1 → 降级为 ASK
- 证据维度 >= 2 → 允许生成 AUTO-FIX 指令

## D-07: 后置条件
- 修复指令已生成并嵌入审查报告
- 指令格式可被 ASP 编排器机器解析

## D-08: 副作用
- 无副作用（只生成指令，不执行修复）

## D-09: 性能要求
- **响应时间**: 单个指令生成 < 1 秒
- **吞吐量**: 每次审查 0~20 个修复指令
- **资源消耗**: 低

## D-10: 安全要求
- **数据隐私**: 不上传用户文档
- **权限控制**: 只读取（不修改任何文件）
- **输入验证**: 验证证据充分性

## D-11: 并发要求
- **并发模式**: 无并发需求
- **冲突处理**: 不适用

## D-12: 数据一致性
- **幂等性**: 同一 Finding 重复生成产生相同指令
- **一致性保证**: 指令内容与 Finding 一致

## D-13: 可观测性
- **日志**: 修复指令嵌入审查报告
- **追踪**: 通过 finding_id 追踪

## D-14: 部署约束
- **运行环境**: Claude Code CLI
- **依赖**: 无外部依赖

## D-15: 依赖关系
- **上游依赖**: FT-005（决策引擎，提供 AUTO-FIX 决策）
- **下游依赖**: FT-008（编排器协议，消费修复指令）、FT-009（归档体系）
- **Feature 依赖**: FT-005

## D-16: 实现映射
- **入口文件**: `skills/pb-review-v2/SKILL.md`（Workflow 第 5 步）
- **核心逻辑**: 基于 Finding 和 Evidence 生成结构化 YAML 指令
- **配置文件**: `references/audit-template.md`（修复指令模板）
