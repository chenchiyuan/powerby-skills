## 七、常见问题（FAQ）

### Q1: 改造工作量太大，能否分阶段实施？

**A:** 可以。建议按照第11章的推荐实施顺序：
1. 先修功能闭集问题（2-4周）
2. 再修feature原子化问题（1-2周）
3. 再补oracle和fixture contract（3-4周）
4. 再补测试追踪矩阵（1周）
5. 最后新增testability scorecard和test-case index（1周）

### Q2: 如何判断某个功能是否达到test_ready状态？

**A:** 参考第7章的12项检查清单：
- [ ] 功能已原子化
- [ ] 输入参数完整
- [ ] 正常输出有明确schema和字段级oracle
- [ ] 异常输出有错误码和触发条件
- [ ] 边界值清单完整
- [ ] 后置条件可断言
- [ ] 副作用可断言
- [ ] 上下游依赖明确
- [ ] 外部依赖替身策略明确
- [ ] 最小fixture数据集明确
- [ ] 已定义测试组索引
- [ ] 已定义coverage claim边界

### Q3: 如何处理遗留代码的测试化改造？

**A:** 建议采用"增量改造"策略：
1. 优先改造核心功能（高频使用、高风险）
2. 每次迭代改造3-5个功能
3. 新功能必须按照新标准编写
4. 遗留功能在修改时同步改造

### Q4: 改造后的文档如何维护？

**A:** 建议建立以下维护机制：
1. 每次迭代都更新功能地图（新增/修改/删除功能）
2. 每次迭代都更新测试用例索引
3. 每月审查一次testability scorecard
4. 每季度审查一次gap-analysis

### Q5: 如何衡量改造的成功？

**A:** 参考第12章的最终成功标准：
1. 对任意项目输出完整功能地图（功能闭合集合完成率=100%）
2. 对任意功能输出完整规格卡和测试断言矩阵（oracle完整率≥90%）
3. 基于文档直接生成完整测试用例索引（测试追踪完整率=100%）
4. 任何一个功能都能明确知道：要测什么、不测什么、用什么数据测、成功时断言什么、失败时断言什么、通过后能覆盖哪条需求和哪条业务规则
