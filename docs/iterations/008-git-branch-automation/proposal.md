# Proposal: Git分支自动化管理

**迭代编号**: 008
**迭代名称**: git-branch-automation
**创建日期**: 2026-03-06
**状态**: Draft

---

## 1. 产品定位

### 目标用户
- **角色**: 使用PowerBy Skills的开发者（个人或小团队）
- **场景**: 在项目中使用GitFlow工作流程进行迭代开发
- **痛点**: 迭代开始后没有正确开启Git分支，都在main分支上开发，导致代码管理混乱、无法回滚、难以并行开发等问题

### 核心价值
**自动化Git分支管理，让开发者专注于功能实现，而不是手动管理分支，确保每个迭代在独立的feature分支上开发，遵循Git最佳实践。**

### 成功指标
- **分支创建成功率**: 100%（每个新迭代都自动创建feature分支）
- **分支命名规范符合率**: 100%（所有分支命名符合`feature/{id}-{name}`格式）
- **分支合并成功率**: ≥95%（大部分迭代能顺利合并到develop分支）
- **用户满意度**: 开发者反馈不再需要手动管理分支，工作流程更流畅

## 2. 需求清单

### 必须实现（P0 - 核心功能）

| ID | 需求描述 | 优先级 | 验收标准（草案） |
|----|---------|--------|----------------|
| REQ-001 | 迭代创建时自动创建Git分支 | 必须 | 1. 执行`/powerby-asp`或`/powerby.define`时自动创建feature分支<br>2. 分支命名格式为`feature/{迭代编号}-{迭代名称}`<br>3. 从develop分支创建<br>4. 创建后自动切换到该分支<br>5. 分支信息记录到`.powerby/iterations.json` |
| REQ-002 | 迭代状态追踪增强 | 必须 | 1. `.powerby/iterations.json`增加`branch_info`字段<br>2. 包含：分支名称、状态、创建时间、合并时间、源分支、目标分支<br>3. 分支状态：`active`/`merged`/`deleted`<br>4. 状态变更时自动更新JSON文件 |
| REQ-003 | 迭代完成时自动合并分支 | 必须 | 1. P8阶段完成后提示用户合并分支<br>2. 合并目标为develop分支<br>3. 使用`git merge --no-ff`保留提交历史<br>4. 合并成功后更新分支状态为`merged`<br>5. 合并失败时提供清晰的错误信息和解决建议 |
| REQ-004 | 分支清理机制 | 必须 | 1. 合并完成后询问用户是否删除feature分支<br>2. 用户确认后删除本地和远程分支<br>3. 删除成功后更新分支状态为`deleted`<br>4. 用户选择保留时状态保持为`merged` |
| REQ-005 | 分支状态检查 | 必须 | 1. P1开始时检查是否在正确的feature分支上<br>2. P6开始时检查是否有未提交的更改<br>3. P8开始时检查是否与远程分支同步<br>4. 检查失败时提供清晰的提示和修复建议<br>5. 检查通过后才允许继续执行后续流程 |

### 应该实现（P1 - 增强功能）

| ID | 需求描述 | 优先级 | 验收标准（草案） |
|----|---------|--------|----------------|
| REQ-006 | 分支切换提示 | 应该 | 1. 检测到用户在错误的分支上工作时显示警告<br>2. 提示包括：当前分支、应该在的分支、切换命令<br>3. 提供一键切换功能（用户确认后自动执行） |
| REQ-007 | 分支冲突检测 | 应该 | 1. 合并前执行`git merge --no-commit --no-ff`检测冲突<br>2. 存在冲突时列出冲突文件清单<br>3. 提供冲突解决指南<br>4. 冲突解决后可继续合并流程 |
| REQ-008 | 分支历史可视化 | 应该 | 1. 迭代完成时生成分支历史报告（Markdown格式）<br>2. 报告包含：提交历史、分支图（Mermaid）、合并记录<br>3. 报告保存到`docs/iterations/{id}-{name}/branch-history.md` |

### 可选实现（P2 - 可推迟）

| ID | 需求描述 | 优先级 | 验收标准（草案） |
|----|---------|--------|----------------|
| REQ-009 | 多迭代并行开发支持 | 可选 | 1. 允许用户在多个feature分支之间切换<br>2. 切换分支时自动保存当前工作状态<br>3. 提供分支列表查看功能 |
| REQ-010 | 自动推送到远程仓库 | 可选 | 1. 分支创建后自动推送到远程仓库<br>2. 每次提交后自动推送（可配置）<br>3. 推送失败时提供重试机制 |
| REQ-011 | 分支保护规则集成 | 可选 | 1. 集成GitHub分支保护规则检查<br>2. 检查PR审查要求、状态检查、签名提交<br>3. 不符合规则时阻止合并 |

## 3. 明确排除

| ID | 排除项 | 排除理由 |
|----|--------|---------|
| EXC-001 | 自动解决合并冲突 | 合并冲突需要人工判断，自动解决可能导致代码错误 |
| EXC-002 | 支持其他Git工作流（如GitHub Flow、Trunk-Based） | 当前需求明确使用GitFlow，支持其他工作流会增加复杂度 |
| EXC-003 | Git Hooks自动安装 | Git Hooks安装属于`powerby-git`技能的职责，不在本次需求范围 |
| EXC-004 | 分支权限管理 | 权限管理属于GitHub/GitLab平台层面，不在PowerBy Skills范围 |

## 4. 约束条件

| ID | 约束描述 |
|----|---------|
| CON-001 | **Git环境依赖**: 项目必须是Git仓库，必须存在develop分支，用户必须有分支创建和合并权限 |
| CON-002 | **技术栈约束**: 必须使用GitFlow工作流程，分支命名必须遵循`feature/{id}-{name}`格式，合并策略必须使用`--no-ff`保留历史 |
| CON-003 | **用户交互约束**: 所有破坏性操作（合并、删除）必须用户确认，分支创建可以自动执行（非破坏性），错误信息必须清晰且提供解决方案 |
| CON-004 | **兼容性约束**: 必须与现有的`powerby-github-branch`技能兼容，必须与P0-P8生命周期流程集成，不能破坏现有的迭代追踪机制 |

## 5. 现有能力复用分析

### 可直接复用的能力
- `powerby-github-branch`技能的基础分支管理能力
- `powerby-git`技能的Git状态检查能力
- `.powerby/iterations.json`的迭代追踪机制

### 需要扩展的能力
- `powerby-github-branch.create_feature_branch()` - 扩展为自动触发

- `.powerby/iterations.json` - 扩展为包含分支状态信息

### 需要全新开发的能力
- 分支切换提示机制（REQ-006）
- 分支冲突检测机制（REQ-007）
- 分支历史可视化报告（REQ-008）

## 7. 风险评估

### 高风险项
- **风险**: 与现有`powerby-github-branch`技能的集成可能存在冲突
- **缓解措施**: 详细分析现有技能的实现，确保扩展而非重写

### 中风险项
- **风险**: 用户可能在错误的分支上进行了大量工作，切换分支会丢失工作
- **缓解措施**: 在切换分支前检查未提交的更改，提示用户先提交或暂存

### 低风险项
- **风险**: 分支合并可能存在冲突
- **缓解措施**: 提供冲突检测和解决指南，不自动解决冲突
