# Proposal: OHLCV 价格接受度地图

**迭代编号**: 013
**项目名称**: ohlcv-price-acceptance-map
**创建日期**: 2026-03-30
**状态**: Draft

---

## 0. Upstream Design Input

- **来源文档**: `design-brief.md`
- **目标摘要**:
  - 基于单个交易对、单个周期、最近 N 根 OHLCV，构建一张可解释的价格接受度地图
  - 主目标是识别历史结构共识区 / 支撑阻力观察区
  - 输出既要能给人工交易员看，也要能被程序消费
- **验证方式**:
  - 一期优先验证“结构解释有效”
  - 即高概率区域是否能对应历史上的筹码密集区、反复震荡区或直观可解释的支撑阻力区
- **推荐方向**:
  - 一期不把未来 `H` 根事件概率作为主定义
  - 核心算法定义为 `price_acceptance_probability`
  - 单根 K 线的 `time_weight * volume` 在其 `[low, high]` 覆盖到的底层价格单元中均匀分配
  - 底层先构建 `micro acceptance map`，再由独立区域划分服务聚合成区域级输出

---

## 1. 产品定位

- **目标用户**:
  - 主要：人工交易员
  - 次要：消费结构化结果做过滤、打分或展示的策略程序

- **核心价值**:
  - 把依赖经验的支撑阻力 / 共识区判断，收敛成可复现、可解释、可序列化输出的价格接受度地图
  - 为人工分析提供热力图和区域列表
  - 为后续 CLI、Web 和程序接口提供统一合同输入

- **成功指标**:
  1. 对同一组 OHLCV 输入，服务能稳定输出一致的价格接受度结果
  2. 结果可被 CLI 以 JSON 返回，并被 Web 页面直接消费
  3. 主用户可通过热力图和区域列表识别出历史高接受度价格区
  4. 产品合同不混入架构实现、未来事件预测或交易信号定义

## 2. 需求清单

| ID | 需求描述 | 优先级 | 验收标准（草案） | 复用策略 |
|----|---------|--------|----------------|---------|
| REQ-001 | 服务必须接收单个交易对、单个周期、最近 N 根 OHLCV 作为一次分析输入 | 必须 | 输入契约明确要求同一资产、同一周期、时间升序、连续；`N` 为用户自定义正整数，默认值 `500` | 全新开发 |
| REQ-002 | 服务必须基于历史 OHLCV 生成底层 `micro acceptance map` | 必须 | 一期默认把历史价格总区间切成 `100` 个 `micro bins`，并能输出每个价格单元的基础概率分布 | 全新开发 |
| REQ-003 | 核心概率必须定义为 `price_acceptance_probability` | 必须 | 对每根 K 线，`time_weight * volume` 在 `[low, high]` 覆盖到的 `micro bins` 中均匀分配；总结果可归一化为价格接受度概率分布 | 全新开发 |
| REQ-004 | 时间权重服务必须支持可扩展口径，一期默认实现指数衰减 | 必须 | 一期产物中存在时间权重配置位，默认使用指数衰减，且不强制引入其他衰减实现 | 全新开发 |
| REQ-005 | 区域划分服务必须与底层概率计算解耦 | 必须 | 区域服务消费底层价格分布，输出完整覆盖历史价格范围、且互不重叠的区域集合 | 全新开发 |
| REQ-006 | 一期区域划分服务至少支持波动自适应切分与等宽切分两种插件 | 必须 | 调用方可在两种区域插件之间切换，且两者都能产出可聚合的区域集合；`equal_width` 默认按每 `5` 个 `micro bins` 组成一个区域；`adaptive_volatility` 默认基于最新 `ATR_20` 与 `micro_bin_width` 的比值推导区域组宽，即 `adaptive_group_size = max(1, round(ATR_20 / micro_bin_width))` | 全新开发 |
| REQ-007 | 区域级输出必须支持热力图全貌与区域列表结论两种消费形态 | 必须 | JSON 输出中同时具备价格轴/区域级概率数据和排序后的区域结果，足以支撑 CLI 与 Web 可视化 | 全新开发 |
| REQ-008 | 服务必须输出最小必要的诊断字段，帮助解释主概率的来源 | 应该 | 除主概率外，至少保留 `coverage_count`、`weighted_volume_contribution` 或等价诊断字段 | 全新开发 |
| REQ-009 | 需要提供 CLI 入口，支持返回结构化 JSON | 必须 | 用户可通过 CLI 输入 OHLCV 数据文件，得到稳定 JSON 输出；若未显式指定 `partition_mode`，默认使用 `equal_width` | 扩展现有 |
| REQ-010 | 需要提供 Web 页面展示价格接受度热力图和区域列表 | 应该 | Web 页面至少能加载一次分析结果，并展示热力图全貌与区域列表 | 全新开发 |
| REQ-011 | 服务必须提供基础合法性校验与可解释错误反馈 | 必须 | 对 `N <= 0`、字段缺失、非同周期、非升序等输入给出明确错误而非静默失败 | 扩展现有 |
| REQ-012 | 一期默认主市场为加密货币，但设计上应保持对其他市场的可泛化性 | 应该 | 合同文档不写死只支持加密货币，参数和字段命名不依赖单一市场术语 | 全新开发 |

## 3. 明确排除

| ID | 排除项 | 排除理由 |
|----|--------|---------|
| EXC-001 | 未来 `H` 根事件概率作为一期主定义 | 用户已明确一期主目标是结构共识区识别，不是前瞻触达预测 |
| EXC-002 | Monte Carlo 终点分布融合为一期核心算法 | 参考 demo 可作为后续扩展，但当前会把结构接受度与未来概率混淆 |
| EXC-003 | tick size 对齐、盘口微观结构、委托簿建模 | 当前输入只有 OHLCV，一期不应引入无法支撑的数据层假设 |
| EXC-004 | 交易建议、自动下单信号、仓位决策 | 本服务定位是概率与结构识别，不是交易执行引擎 |
| EXC-005 | 复杂脏数据修复、缺口补全、跨市场数据标准化 | 一期只做基础合法性校验，避免把数据治理与算法验证混成一件事 |
| EXC-006 | 架构设计、数据库、API、部署方案 | 这些属于后续 `powerby-asp-architect` 阶段，不在产品合同阶段锁定 |

## 4. 约束条件

| ID | 约束描述 | 影响范围 |
|----|---------|---------|
| CON-001 | `proposal.md` 必须可回溯到 `design-brief.md` 的问题定义、验证方式与推荐方向 | 合同边界 |
| CON-002 | 一期主验收是算法正确性与 JSON 输出正确性，CLI/Web 不得反向主导算法定义 | 范围优先级 |
| CON-003 | 一期主用户是人工交易员，因此可解释性优先于复杂预测模型 | 算法与输出设计 |
| CON-004 | 一期只接受基于 K 线区间覆盖近似“到达和停留”，不假设可获得真实 intrabar 时间分布 | 概率定义 |
| CON-005 | 底层默认 `micro_bins = 100`，作为一期合同默认值 | 参数默认值 |
| CON-006 | 时间权重服务要为多口径预留扩展位，但一期只实现指数衰减 | 参数扩展性 |
| CON-007 | 区域划分服务必须与核心概率计算分层，且区域必须完整覆盖历史价格范围、彼此不重叠 | 模块边界 |
| CON-008 | 不允许在产品阶段写入数据库结构、API 协议、部署架构或实现映射 | 阶段边界 |
