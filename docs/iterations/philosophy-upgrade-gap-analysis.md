# pb-v1 Skills 三大支柱差距分析

**日期**: 2026-04-01  
**目标**: 对照 skill-design-protocol.md v3.0 三大支柱，分析 4 个已完成 skill 的差距

---

## 核心问题

所有 skill 的「核心哲学」都是**用途陈述**，不是**策略哲学**。

| Skill | 当前核心哲学 | 问题 |
|-------|------------|------|
| orchestrator | "维护流程状态，提供执行建议。不控制调用..." | 在描述"做什么"，不是教模型"怎么想" |
| discovery | "需求收敛不是记录需求���是通过 MVP 分解..." | "不是X是Y"句式 = 用途对比，不是思考框架 |
| drafting | "规格拆解不是创造功能，是将 proposal.md..." | 同上，描述职责范围，不是校准认知 |
| designing | "架构收敛不是产出漂亮的架构图，是通过..." | 同上，描述价值主张，不是判断锚点 |

**检验方法**：把这些核心哲学放到全新项目/场景中，能指导模型做出正确判断吗？  
**答案**：不能。它们只描述了 skill 的定位，没有提供判断框架。

## 逐 Skill 差距分析

### 1. pb-v1-orchestrator

**当前状态**：用途声明 + 6条设计原则（偏操作规则）

**需要的策略哲学**：

模型惯性（需要对抗）：
- "编排器 = 自动调度/代理调用" → 实际上只是状态快照 + 风险顾问
- "流程 = 严格顺序执行" → 实际上跳步是合法的，只是需要风险评估
- "状态不一致 = 错误" → 实际上中间态是常态，需要识别而非拒绝

缺失的判断框架：
- 判断"当前状态下最安全的下一步"的思考方式
- 何时建议跳步、何时建议回退的判断锚点
- 状态快照的准确性 > 流程建议的全面性

**支柱二（工具/能力边界）差距**：当前没有明确的工具边界声明  
**支柱三（事实说明）差距**：当前没有惰性知识补足

---

### 2. pb-v1-discovery

**当前状态**：用途声明 + 6条设计原则（偏操作规则）

**需要的策略哲学**：

模型惯性（需要对抗）：
- "需求收敛 = 问用户更多细节" → 实际上是证伪——假定不需要，直到证明必须
- "MVP = 砍掉功能" → 实际上 MVP 是找到最小充分集，不是做减法
- "用户说要的就是需要的" → 实际上需要区分"用户想要"和"用户需要"
- "收敛 = 用户说够了" → 实际上收敛 = 信息增量归零

缺失的判断框架：
- 每个功能点的证伪思维（默认不需要，直到证明必须）
- 收敛的客观标准（信息增量，不是主观感觉）
- "用户想要"和"真正需要"的区分能力

**支柱二差距**：当前没有工具/能力边界  
**支柱三差距**：当前没有事实说明层

---

### 3. pb-v1-drafting

**当前状态**：用途声明 + 6条设计原则（偏操作规则）

**需要的策略哲学**：

模型惯性（需要对抗）：
- "规格 = 尽可能详细的描述" → 实际上规格是可验证的契约，不是描述
- "拆解 = 均匀分解" → 实际上粒度由可验证性决定，不是均匀分配
- "写得越多越好" → 实际上无法转化为测试的维度是噪音
- "先写完再检查" → 实际上边写边验证可追溯性

缺失的判断框架：
- 每个维度的价值 = 它能生成几个测试用例
- 粒度判断：如果一个 Feature 包含两个独立可验证的行为，它该拆
- 完整性判断：D-01~D-08 的每条都有对应的 D-17~D-20 验证

**支柱二差距**：当前没有工具/能力边界  
**支柱三差距**：当前没有事实说明���

### 4. pb-v1-designing

**当前状态**：用途声明 + 8条设计原则 + 架构原则快照（最丰富，但仍是规则列表）

**需要的策略哲学**：

模型惯性（需要对抗）：
- "架构 = 画漂亮的架构图" → 实际上是决策链，图只是副产品
- "设计 = 从零选方案" → 实际上起点是现有代码，不是白纸
- "每个问题都需要用户决策" → 实际上只有 L1 需要，L2/L3 自主
- "架构完成 = 文档完成" → 实际上完成 = Self-Check Gates 通过

缺失的判断框架：
- 决策起点：现有代码已经做了什么？增量路径可行吗？
- 决策分级的自主判断（L1/L2/L3 的切换条件）
- 收敛标准：Self-Check Gates，不是文档完整度

**支柱二差距**：当��有职责边界但不是"工具/能力边界"格式  
**支柱三差距**：当前设计原则中混入了应该是事实说明的内容

## 升级策略

1. 为每个 skill 识别领域特定的模型惯性
2. 将「核心哲学」从用途声明改写为闭合的思考框架
3. 确保思考框架通过检验：换项目仍有效
4. 补充支柱二（工具/能力边界）和支柱三（事实说明）的内容
5. 将原设计原则中属于事实说明的内容迁移到正确位置

**升级顺序**：orchestrator → discovery → drafting → designing（从简到繁）
