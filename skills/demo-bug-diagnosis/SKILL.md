# Bug Diagnosis

Use this skill to diagnose bugs, test failures, and production anomalies.
Apply it when the user reports unexpected behavior, error messages, or test failures.
Do not rely on it for feature implementation, performance optimization, or code refactoring.

## Purpose

将模糊的"它坏了"转化为精确的"根因是 X，证据链是 A→B→C"。成功的诊断是一份可验证的结论，而非一次碰运气的修复。

**红线声明**（三明治结构前置，与 Safety 对应）：
- 诊断与修复分离——诊断过程中不修改生产代码
- 不基于猜测输出根因——"可能是 X"和"根因是 X"有本质区别
- 不跳过预期行为定义——没有基准就没有"Bug"

## Success criteria

- 输出唯一根因，附带完整证据链（每步可回溯）
- 根因可通过最小复现用例独立验证
- 诊断过程中未引入任何代码变更（诊断与修复分离）
- 失败时：明确声明"证据不足，无法定位"，列出已排除项和下一步建议

## Strategy

> **Bug 诊断是证据收敛：每一步操作都是在缩小嫌疑范围，不是在尝试修复。**

**对抗的模型惯性**：

| 模型惯性 | 真实情况 |
|---------|---------|
| 看到错误信息就直接改代码 | 错误信息是症状，不是根因。先收集证据 |
| 搜到 StackOverflow 答案就套用 | 答案是线索不是结论，需验证是否匹配当前上下文 |
| 改了不报错就算修好了 | 症状消失 ≠ 根因消除，必须有回归测试证明 |
| 一次改多处"试试看" | 每次只改一个变量，否则无法归因 |
| 复杂问题一定需要复杂分析 | 80% 的 Bug 根因是简单的——拼写错误、边界遗漏、顺序错误 |

**思考框架**：

1. **先定义"正常"** — 在追查"哪里错了"之前，先确认"正确行为应该是什么"
2. **收集证据，不收集猜测** — 日志、堆栈、git diff、最小复现，每一步产出的是证据
3. **二分法缩小范围** — 不从头到尾排查，而是不断把嫌疑范围切半
4. **根因唯一性验证** — 找到疑似根因后，验证"修复它是否充分"且"不修复它是否必然复现"

**判断锚点**：

- **成功标准**：根因唯一确定 + 证据链完整 + 最小复现可验证
- **切换条件**：证据指向环境问题时切换到运维排查；证据指向需求歧义时回退到需求澄清
- **停止条件**：3 轮证据收集后仍无法缩小范围 → 停止，输出已知证据和排除项

## Tools and capability boundaries

**原子行为抽象**：诊断 = 观察 + 定位 + 复现 + 验证

| 行为 | 工具 | 适用场景 | 不适用场景 |
|------|------|---------|-----------|
| 观察 | 日志分析（Read + Grep） | 有日志输出的场景 | 日志被关闭或不完整 |
| 定位 | git bisect / git log / git blame | 回归类 Bug（曾经正常） | 首次实现就存在的缺陷 |
| 复现 | 最小复现脚本（Bash） | 可确定性复现的 Bug | Heisenbug / 并发竞态 |
| 验证 | 单元测试 / 断言 | 根因假设需要验证时 | 需要完整集成环境的场景 |

**Harness 层工具（代码接管，见 5.4）**：

| 工具 | 类型 | 职责 | 说明 |
|------|------|------|------|
| `scripts/collect-context.sh` | Guide（前馈） | 收集初始证据 | 确定性操作：git 历史、环境信息、错误日志 |
| `scripts/validate-report.sh` | Sensor（反馈） | 校验诊断报告完整性 | 结构校验：必填字段、证据链非空、根因非空 |

**边界声明**：
- 本 Skill 只负责诊断，不负责修复实现
- 环境类问题（权限、网络、配置）超出本 Skill 范围，输出线索后交给运维
- 不修改生产代码，诊断过程中的任何代码变更仅限于测试/复现脚本

**职责边界（代码 vs AI）**：

| 逻辑 | 归属 | 理由 |
|------|------|------|
| 收集 git 历史、环境信息 | **代码**（collect-context.sh） | 确定性操作，每次结果一致 |
| 校验报告字段完整性 | **代码**（validate-report.sh） | 结构校验，"有就是有，没有就是没有" |
| 分析错误日志、推断根因 | **AI** | 需要理解上下文和语义推理 |
| 形成假设并排序 | **AI** | 需要策略性思维和多角度评估 |
| 判断根因唯一性 | **AI** | 需要推理"充分且必要" |

## Important facts and constraints

1. **错误信息 ≠ 根因** — 错误信息描述的是"症状发生在哪里"，根因往往在调用链的更上游
2. **最近的变更是最大嫌疑人** — 回归类 Bug 中，`git log --since` 和 `git bisect` 是最高效的定位手段
3. **Heisenbug 真实存在** — 观察行为本身会改变 Bug 表现（加日志后 Bug 消失），此时需要非侵入式手段
4. **并发 Bug 的复现需要压力** — 单线程跑一次不复现不代表没问题，需要并发/压力条件
5. **环境差异是隐形杀手** — "在我电脑上能跑"是最常见的误判。环境变量、依赖版本、OS 差异都是嫌疑人
6. **一次只改一个变量** — 同时改两处，无论 Bug 是否消失，都无法确定是哪个改动生效

## Workflow

1. **定义预期行为** — 从需求/测试/文档中确认"正确的行为应该是什么"
2. **收集初始证据** — 运行 `scripts/collect-context.sh` 收集错误日志、堆栈、最近变更（代码接管，确定性）
3. **形成假设** — 基于证据提出 ≥2 个可能的根因假设，按可能性排序（AI 判断）

### Gate: 假设质量验证
**触发条件**: 形成假设之后、开始验证之前
**验证内容**: 每个假设是否有至少一条支撑证据；假设之间是否互斥
**通过标准**: ≥2 个假设，每个有证据支撑，且假设覆盖了已知证据
**未通过处理**: 回退到 Step 2 补充证据收集

4. **二分验证** — 从最可能的假设开始，通过测试/日志/bisect 验证或排除（每次只验证一个假设）

### Gate: 根因唯一性验证
**触发条件**: 疑似根因锁定之后、输出报告之前
**验证内容**: "修复它是否充分"（修复后 Bug 消失）且"不修复它是否必然复现"（不修复则 Bug 必现）
**通过标准**: 两个条件同时满足
**未通过处理**: 当前假设降级为"疑似"，回退到 Step 4 验证下一个假设

5. **锁定根因** — 通过 Gate 验证的唯一根因
6. **输出诊断报告** — 填写诊断报告模板，运行 `scripts/validate-report.sh` 校验完整性（代码接管，Sensor）

## Output format

```markdown
# Bug 诊断报告

## 症状描述
[用户报告的现象]

## 预期行为
[正确行为应该是什么]

## 根因
[唯一确定的根因]

## 证据链
1. [证据 1] → 排除了 [假设 A]
2. [证据 2] → 缩小范围到 [模块 X]
3. [证据 3] → 确认根因是 [具体原因]

## 最小复现
[复现步骤或脚本]

## 修复建议
[建议的修复方向，不包含具体实现]

## 已排除项
- [排除的假设及排除理由]
```

## Subtask / parallelism guidance

- 证据收集（Step 2）可并行：日志分析、git 历史、环境检查同时进行
- 假设验证（Step 4）必须串行：一次只验证一个假设，否则无法归因
- 不允许跳过 Step 1（定义预期行为）直接进入证据收集

## Examples

**Example 1**
Input: "用户登录后 token 过期时间不对，应该是 24 小时但实际只有 1 小时"
Output: 诊断报告，根因：`config/auth.js` 中 `expiresIn` 单位是秒而非小时，`3600` 被解释为 3600 秒 = 1 小时。证据链：git blame 定位到最近的配置变更 + 单元测试验证。

**Example 2**
Input: "CI 测试随机失败，本地跑都能过"
Output: 诊断报告，根因：测试依赖了全局状态（共享数据库连接），并行执行时产生竞态。证据链：CI 日志中失败总发生在并行 job + 本地串行跑 100 次不失败 + 隔离数据库连接后 CI 通过。

## Safety

诊断完成前的强制自检（三明治结构后置，与 Purpose 红线声明对应）：

- [ ] **诊断与修复分离** — 诊断过程中未修改任何生产代码（仅限测试/复现脚本）
- [ ] **根因有证据支撑** — 未基于猜测输出根因；证据不足时已声明"无法定位"
- [ ] **事实与推断分离** — 未把推断写成事实；"可能是 X"和"根因是 X"已明确区分
- [ ] **预期行为已定义** — 未跳过 Step 1 直接诊断；有明确的"正确行为"基准
- [ ] **报告结构完整** — `scripts/validate-report.sh` 校验通过
