# Proposal: PowerBy Architecture Design (架构设计流程)

## 1. 产品定位

- **目标用户**：极客开发者/架构师，已通过 ASP 流程完成产品文档交付，需要将产品规格转化为高质量架构设计。
- **核心价值**：用户触发架构设计流程后，系统自动完成「苏格拉底式架构澄清 → 架构设计 → 多 AI 对抗审查 → 自我修正 → 可视化交付」全流程，产出逻辑自洽、与产品文档双向对齐、接口/协议定义完整的架构文档。
- **成功指标**：
  - 用户通过独立命令触发架构设计流程
  - architecture.md 中每个功能点（FP-xxx）有对应架构设计（正向覆盖率 100%）
  - architecture.md 中不存在超出产品文档范围的架构设计（反向溢出率 0%）
  - 所有架构疑问在设计前通过苏格拉底式澄清解决，前期充分沟通减少后期返工
  - arch_logs/ 目录中至少包含一轮 Reviewer 审查报告

## 2. 需求清单

| ID | 需求描述 | 优先级 | 验收标准（草案） |
|----|---------|--------|----------------|
| REQ-001 | **架构师角色定义**：定义 Architect Agent，基于已交付产品文档（proposal.md、spec.md、function-points.md、product-map.md）产出 `architecture.md`，包含系统架构、组件划分、数据流、接口定义等完整架构内容 | 必须 | architecture.md 包含系统架构、组件划分、数据流、接口/协议定义等完整架构内容 |
| REQ-002 | **苏格拉底式架构澄清**：正式设计前，Architect 通过多轮苏格拉底式提问穷尽所有架构疑问（选型、边界、约束、风险等）。不限轮次，以"没有疑问"为结束条件。前期聊得越充分，后期问题越少 | 必须 | 所有架构疑问在设计前解决，澄清记录可追溯，以双方达成共识为结束条件 |
| REQ-003 | **多轮架构审查机制**：最多 5 轮，默认审查序列 [Claude, Codex, Claude, Codex, Claude]，每轮 review 必须尽可能全面发现问题，支持用户自定义序列。超限触发 ESCALATION | 必须 | 审查报告独立存储在 `arch_logs/round-{N}-{reviewer}.md`，STATUS 为 PASS/FAIL |
| REQ-004 | **宪法符合性审查**：审查架构是否符合 constitution.md 原则（原子服务契约、Fail-Fast 纪律等） | 必须 | 审查报告包含宪法符合性检查结果，引用具体宪法条款 |
| REQ-005 | **双向覆盖检查（架构↔产品）**：正向覆盖（function-points.md 每个 FP 在架构中有对应设计）+ 反向溢出（架构不能多设计）+ 排除项入侵检查。超出范围需用户审批 | 必须 | 审查报告包含 Coverage Matrix（FP-xxx ↔ 架构组件），覆盖所有功能点 |
| REQ-006 | **复用现有 Skill 协议**：架构 Skill 和审查 Skill 参考 powerby-asp-reviewer 等现有 Skill 的格式和输出规范进行优化 | 必须 | Skill 文件遵循现有 frontmatter + Markdown 规范，输出格式机器可读 |
| REQ-007 | **接口/协议规范定义**：架构阶段定义 API 契约、数据结构、服务间通信协议等协议级规范，禁止生成任何业务代码 | 必须 | architecture.md 包含接口/协议定义章节，不含任何业务代码 |
| REQ-008 | **用户触发的独立流程**：产品文档交付后由用户主动触发架构设计流程，独立于产品 ASP 流程 | 必须 | 流程通过独立命令触发，不与产品 ASP 流程耦合 |
| REQ-009 | **架构可视化**：使用 Mermaid + Markdown 产出用户友好的架构图（组件图、数据流图、部署图等），文档清晰易读 | 必须 | architecture.md 包含有效的 Mermaid 架构图，语法校验通过 |
| REQ-010 | **架构变更标注**：在整体架构图中清晰标注新增/变更部分，使用颜色或标记突出显示，便于用户快速识别变更点 | 必须 | 变更部分在架构图中使用显著标记突出显示 |
| REQ-011 | **技术选型对比流程**：如有技术选型对比，在架构交付后逐条清晰列举选型方案及优劣。用户给出整体答复后，重新进入架构设计和 review 环节 | 应该 | 选型对比以结构化表格呈现（方案、优点、缺点、推荐理由），用户确认后触发架构修订 |
| REQ-012 | **Codex 自动化审查**：Codex 轮次通过 `codex exec -s read-only` 自动执行，无需用户手动中转 | 应该 | Codex 审查自动执行，输出格式与 Claude 审查一致 |

## 3. 明确排除

| ID | 排除项 | 排除理由 |
|----|--------|---------|
| EXC-001 | 业务代码生成 | 架构阶段仅定义接口/协议规范，不产生任何业务代码 |
| EXC-002 | 任务拆解（tasks.md） | 不在架构设计范围内，由后续阶段处理 |
| EXC-003 | 跨迭代架构关联 | 复杂度高，MVP 不需要 |

## 4. 约束条件

| ID | 约束描述 |
|----|---------|
| CON-001 | **实现载体约束**：所有功能通过 Skill 提示词文件（SKILL.md）和命令文件（.claude/commands/*.md）实现，不写业务代码 |
| CON-002 | **流程隔离约束**：架构设计流程独立于产品 ASP 流程，禁止混淆命名、阶段、角色、产物 |
| CON-003 | **产品文档依赖约束**：架构设计以已交付的产品文档（proposal.md、spec.md、function-points.md、product-map.md）为输入基准，不可脱离产品文档凭空设计 |
| CON-004 | **宪法依赖约束**：审查基准为 `docs/consitution.md`，该文件必须预先存在 |
| CON-005 | **迭代目录约束**：所有产物存放在 `docs/iterations/{id}-{name}/` 目录，沿用现有迭代管理结构 |
