# 研发协作 3-Gate 卡

> 每个研发任务有 3 个和老板对齐的节点。对齐完继续推进，中间过程我自己把控。

---

## Gate 1：需求边界确认（开工前）

**什么时候做**：接到需求后、写代码之前

**我应该准备**：
- 找到参照物（现有产品、竞品、内部系统），截图串联起来，标注"我们和它哪里不同"。找不到合适参照物时，用 ASCII 草图画出核心页面和流程
- 把 P0 核心用户流程从头到尾串起来，让老板能"走一遍"——用户从哪进来、每一步看到什么、做什么、最终到哪
- 理清范围和优先级：我要做什么、不做什么，哪些是 P0（必须做）、P1（重要可后排）、P2（可选）
- 把不确定的地方列成疑问清单——不确定就问，不猜

**我怎么判断准备好了**：老板看完我的材料，能直接回答"这个流程对不对"，不需要自己脑补任何环节

**我容易踩的坑**：
- 用文字描述交互，老板看完还是不知道页面长什么样——应该给可视化的东西
- 没搞清楚"不做什么"就开工，做到一半发现超出范围
- 不确定的地方自己脑补了，做完才发现和预期不一样
- 把 P1/P2 当 P0 做，核心功能反而没时间

---

## Gate 2：技术方案确认（动手前）

**什么时候做**：需求确认后、正式编码之前

**我应该准备**：
- 技术方案：我打算怎么做，至少准备 2 种方案对比，说明我推荐哪个、为什么
- 任务拆解：拆成可执行的任务列表，每个任务我能说清"做到什么程度算完"
- 关键决策清单：技术选型、架构变更等影响全局的决策，我应该提前列出来让老板拍板，不自己默默定了

**我怎么判断准备好了**：老板能基于我的材料判断"这个方案靠谱"，每个任务有可验证的完成标准

**我容易踩的坑**：
- 只给一个方案没有对比，老板没有判断依据
- 任务拆解太粗（"实现后端"），自己都说不清做到哪算完
- 关键决策自己拍了没沟通，后面发现方向不对要返工

---

## Gate 3：交付确认（上线前）

**什么时候做**：开发完成后、合并/上线之前

**我应该准备**：
- 自检报告：对照 Gate 1 的范围逐项过一遍，P0 功能是否全部实现
- 测试结果：核心功能我自己测过了，正常流程和异常流程都验过
- 演示：能跑起来给老板看

**我怎么判断准备好了**：老板走一遍核心流程没有卡住，P0 功能全部可用

**我容易踩的坑**：
- 自己没测就提交，基本功能跑不通
- P0 功能缺了一个没发现，上线后才暴露
- 只测了正常流程，异常情况一碰就崩

---

## 整体节奏

```
接需求 → [Gate 1: 流程走查+范围+疑问] → 想方案 → [Gate 2: 方案+任务+决策] → 写代码 → [Gate 3: 自检+测试+演示]
```

Gate 之间的过程我自己把控，遇到问题查《研发协作手册》。
