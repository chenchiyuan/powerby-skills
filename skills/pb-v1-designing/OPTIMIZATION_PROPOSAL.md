# pb-v1-designing 优化方案

**版本**: 2.0.0  
**状态**: 方案设计  
**创建日期**: 2026-04-01

---

## 优化背景

### 当前版本的不足

1. **架构不是交互协议** - 只产出架构文档，没有做可实施性收敛
2. **缺少 Scope Challenge** - 没有强制回答"现有代码哪里已解决"、"最小变更集是什么"
3. **缺少强制外显** - 没有强制数据流图、状态机图、测试矩阵
4. **缺少闭环验证** - 没有验证架构是否可实施
5. **缺少反馈机制** - 架构阶段发现的需求问题无法反馈到上游

### 优化目标

**核心目标**：将 pb-v1-designing 从"架构设计"改为"架构收敛"，参照 gstack plan-eng-review

**关键原则**：
1. **架构即交互协议** - 通过架构设计发现澄清问题，让前置需求更清晰
2. **强制外显化** - 数据流、状态机、依赖、测试矩阵必须画出来
3. **可实施性优先** - 围绕 buildable，不围绕漂亮
4. **反馈闭环** - 架构阶段发现的问题可以反馈到 discovery/drafting

## 优化点

### 优化点 1: 新增 Step 0 - Scope Challenge

**问题**: 当前直接进入架构设计，没有先挑战范围和复杂度

**优化**: 在需求对齐后，增加 Scope Challenge 环节

**实施方式**:

```markdown
### Step 0: Scope Challenge（范围挑战）

**目的**: 在设计前先挑战范围，减少不必要的复杂度

**强制回答的问题**:

1. **现有能力盘点**
   - 现有代码哪里已经部分解决了这个问题？
   - 哪些组件可以直接复用？
   - 哪些组件需要扩展？

2. **最小变更集**
   - 最小变更集是什么？
   - 如果超过 8 个文件或 2 个新服务，是否有复杂度 smell？
   - 能否通过配置而非代码解决？

3. **架构模式检查**
   - 每个引入的新架构模式是否已 search 现有实现？
   - 是否在重复造轮子？

4. **依赖检查**
   - 是否引入新的外部依赖？
   - 依赖的稳定性如何？
   - 是否有替代方案？

5. **交付检查**
   - 如果引入新 artifact，是否有 distribution pipeline？
   - 部署复杂度如何？

**产出**: Scope Challenge 报告
```

---
### 优化点 2: 强制中间表示外显化

**问题**: 当前只要求"架构图"，没有强制数据流、状态机、依赖图

**优化**: 强制输出多种中间表示，暴露隐含假设

**实施方式**:

```markdown
### Step 3.5: 强制中间表示（在架构设计后）

**必须产出的图**:

1. **核心架构图**（Mermaid Component Diagram）
   - 组件及其职责
   - 组件间的依赖关系

2. **数据流图**（Mermaid Flowchart）
   - 数据如何在组件间流动
   - 数据转换点
   - 数据持久化点

3. **状态机图**（如适用，Mermaid State Diagram）
   - 核心实体的状态转换
   - 触发条件
   - 副作用

4. **依赖图**（Mermaid Graph）
   - 组件依赖关系
   - 外部依赖
   - 循环依赖检查

5. **测试矩阵**（表格）
   - 每个组件的测试策略
   - 集成测试点
   - E2E 测试场景

**产出**: 5 种中间表示
```

**为什么重要**: LLM 容易在"没画出来"的地方偷懒，强制画图会暴露隐藏假设

### 优化点 3: 交互式决策协议

**问题**: 当前只是"提供方案"，没有交互式决策

**优化**: 将决策评估改为交互式协议，逐个决策

**实施方式**:

```markdown
### Step 4: 交互式决策协议（替代原 Step 4）

**目的**: 不只提供方案，而是引导用户逐个决策

**执行方式**: 使用 AskUserQuestion，每次一个决策点

**决策卡格式**:

```
决策点: {问题描述}

背景: {为什么需要决策}

方案 A: {方案名称}
- 优点: ...
- 缺点: ...
- 复杂度: 低/中/高
- 适合 MVP: 是/否

方案 B: {方案名称}
- 优点: ...
- 缺点: ...
- 复杂度: 低/中/高
- 适合 MVP: 是/否

推荐: 方案 A，因为...
```

**关键约束**:
- 每个决策点单独提问，不批量
- 必须有推荐方案
- 必须说明复杂度和 MVP 适用性
```

**为什么重要**: 避免模型偷偷替用户做关键决策

---
### 优化点 4: 可实施性验证

**问题**: 当前架构设计后没有验证是否可实施

**优化**: 增加可实施性验证环节，围绕 buildable

**实施方式**:

```markdown
### Step 4.5: 可实施性验证（新增）

**目的**: 验证架构是否可实施，不只是漂亮

**强制回答的问题**:

1. **同步 vs 异步**
   - 哪些操作是同步的？
   - 哪些操作是异步的？
   - 异步操作如何通知结果？

2. **重试与幂等**
   - 哪些操作需要重试？
   - 重试策略是什么？
   - 如何保证幂等性？

3. **失败场景**
   - 每个组件的失败场景是什么？
   - 失败后如何恢复？
   - 是否有降级方案？

4. **数据持久化**
   - 数据何时持久化？
   - 持久化失败如何处理？
   - 是否需要事务？

5. **单点故障**
   - 系统的单点故障在哪？
   - 如何避免或缓解？

6. **安全边界**
   - 认证在哪一层？
   - 授权如何实现？
   - 敏感数据如何保护？

**产出**: 可实施性验证报告
```

---
### 优化点 5: 反馈闭环机制

**问题**: 架构阶段发现的需求问题无法反馈到上游

**优化**: 增加反馈机制，允许回退到 discovery/drafting

**实施方式**:

```markdown
### 异常处理增强

**场景 4: 架构设计发现需求问题（新增）**

**触发条件**: 
- Scope Challenge 发现功能点定义不清
- 可实施性验证发现需求矛盾
- 依赖分析发现缺失功能

**处理方式**:
1. 记录发现的问题
2. 标注影响的 Feature
3. 生成反馈报告
4. 建议回退到 pb-v1-discovery 或 pb-v1-drafting
5. 通知 orchestrator

**反馈报告格式**:
```
## 架构反馈报告

### 发现的问题
- 问题 1: {描述}
  - 影响 Feature: F-001, F-003
  - 建议: 回退到 discovery，澄清...

### 建议的修复
- 修复 1: {描述}
  - 修改文档: proposal.md
  - 修改章节: §3.2
```

**产出**: 反馈报告 + 回退建议
```

---
### 优化点 6: 组件与需求映射强化

**问题**: 当前只要求"组件与需求映射"，没有强制验证

**优化**: 强化映射关系，确保每个组件可追溯

**实施方式**:

```markdown
### Step 3.3: 组件与需求映射（增强）

**映射表格式**:

| 组件 | 职责 | 负责的 Feature | 负责的功能点 | 复用/新增 |
|------|------|---------------|-------------|----------|
| AuthService | 用户认证 | F-001, F-002 | [P0] 用户登录<br/>[P0] 密码重置 | 新增 |
| UserRepository | 用户数据访问 | F-001, F-002, F-003 | [P0] 用户登录<br/>[P0] 密码重置<br/>[P1] 用户信息 | 扩展现有 |

**验证规则**:
- [ ] 每个 P0 Feature 都有对应组件
- [ ] 每个组件都有明确的 Feature 映射
- [ ] 没有"孤儿组件"（不负责任何 Feature）
- [ ] 复用组件已标注扩展点
```

## 风险与缓解

### 风险 1: 流程变重，交互轮次增加

**影响**: designing 阶段可能需要 3-5 轮交互

**缓解**:
- Scope Challenge 可以快速完成（5-10 分钟）
- 交互式决策只针对关键决策点（2-3 个）
- 中间表示可以并行生成

### 风险 2: 反馈闭环可能导致流程回退

**影响**: 发现需求问题时需要回退到 discovery

**缓解**:
- 这是好事，早发现早修复
- 回退成本远低于实现后发现问题
- orchestrator 支持回退机制

### 风险 3: 强制外显可能增加文档负担

**影响**: architecture.md 会变长

**缓解**:
- 图比文字更清晰
- 强制外显减少后续沟通成本
- 可以使用模板简化

## 预期收益

### 收益 1: 架构阶段发现需求问题

**量化**: 预计可以在架构阶段发现 30-50% 的需求问题

**价值**: 避免实现后返工

### 收益 2: 架构可实施性提升

**量化**: 减少 "架构很漂亮但无法实现" 的情况

**价值**: planning 和 implementing 阶段更顺畅

### 收益 3: 隐含假设显式化

**量化**: 强制 5 种中间表示，暴露隐藏假设

**价值**: 减少实现阶段的意外

---

## 总结

### 核心变化

1. **新增 Scope Challenge** - 在设计前先挑战范围
2. **强制中间表示** - 5 种图必须产出
3. **交互式决策** - 逐个决策，不批量
4. **可实施性验证** - 围绕 buildable
5. **反馈闭环** - 可以回退到上游
6. **映射强化** - 组件与需求 100% 覆盖

### 设计哲学转变

**从**: 架构设计 = 产出漂亮的架构图  
**到**: 架构收敛 = 通过交互协议让架构可实施

### 与 gstack 的对齐

- ✅ Scope Challenge（对齐 plan-eng-review）
- ✅ 强制中间表示（对齐 diagrams 要求）
- ✅ 交互式决策（对齐 AskUserQuestion 机制）
- ✅ 可实施性优先（对齐 buildable 原则）
- ✅ 反馈闭环（对齐生命周期设计）
