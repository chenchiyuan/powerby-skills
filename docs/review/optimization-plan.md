# Archer 评审报告优化方案

## 文档信息

- 原始文档：`data/archer-pb-review-final.md`
- 优化目标：从"评审报告"升级为"功能规格文档"，支持测试用例编写、架构对照、实现验证
- 审计时间：2026-03-27
- 审计结论：**当前文档是优秀的评审报告，但不是合格的功能规格定义**

---

## 核心矛盾

当前文档回答的是"Archer 做了什么"，而不是"Archer 的每个功能应该怎样工作"。

测试工程师拿到当前文档，无法直接编写测试用例，因为缺少：
- 输入参数规格
- 前置条件定义
- 正常输出格式
- 异常行为描述
- 边界值处理

---

## 问题清单（按严重程度排序）

### P0 - 致命问题

#### 问题 1：功能定义缺少输入/输出/前置/异常规格

**现状**：Section 5 的功能表只有 5 列（ID、功能名、作用、入口、状态），"作用"列只是一句话概要。

**示例**：`F-AS-006 盘后选股` 当前描述：
- 作用：整合 breakout + 智能回调
- 入口：`select_stocks`

**缺失信息**：
- 输入参数：接受哪些参数？必填/可选？
- 前置条件：需要哪些数据已存在？
- 正常输出：输出什么？格式？字段？
- 异常行为：目标日无 K 线怎样？
- 边界值：空结果怎么处理？

**影响范围**：全部 30+ 个功能

**解决方案**：每个功能扩展为独立的功能规格卡

```markdown
### F-AS-006 盘后选股

| 字段 | 内容 |
|---|---|
| 功能 ID | F-AS-006 |
| 功能名 | 盘后选股 |
| 入口 | `select_stocks` |
| 输入参数 | `--date`(可选,默认最近交易日), `--output`(可选,CSV路径) |
| 前置条件 | F-AS-002 已执行, F-AS-005 已执行 |
| 正常输出 | stdout 输出候选股表格 + 可选 CSV 文件 |
| 异常行为 | 目标日无 K 线 → 快速失败并报错 |
| 依赖功能 | F-AS-002, F-AS-005 |
| 验证方式 | `test_select_stocks_command.py` |
| 适用规则 | R-006, R-008 |
```

---

#### 问题 2：功能粒度不一致，无法统一测试

**现状**：功能抽象层级完全不同

**示例对比**：
- `F-AS-010 股票池管理` — 功能集合（增删改查 + 配置 + 指标绑定），至少 5-6 个独立操作
- `F-AS-012 预警指标初始化` — 原子操作
- `F-AS-016 股票分析页 v2` — UI 页面，无行为描述
- `F-AS-014 宏观总览聚合` — 入口是 service 文件名，不是命令

**影响**：一个功能 ID 可能对应 10 个测试场景，另一个只对应 1 个

**解决方案**：统一功能粒度到"单一可测试行为"级别

**拆分示例**：`F-AS-010` 应拆分为：
- F-AS-010a 创建股票池
- F-AS-010b 向池中添加成员
- F-AS-010c 从池中移除成员
- F-AS-010d 启用/停用股票池
- F-AS-010e 为池绑定预警指标

---

### P1 - 严重问题

#### 问题 3：验证矩阵（Section 7）覆盖不全

**现状**：Section 5 定义了 30 个功能，Section 7 只覆盖约 15 个

**缺失功能**：
- F-AS-001 ~ F-AS-005（A 股基础数据、日线、基金 K 线、趋势分析、新高突破）
- F-AS-009（行业趋势查询）
- F-AS-014 ~ F-AS-016（宏观总览、回调总览、分析页）
- F-TK-001, F-TK-002（交易对同步、K 线更新）
- **F-SK-001 ~ F-SK-008（全部 AI Skill 层）— 零覆盖**

**影响**：接近一半的功能无法确认"是否有测试"以及"测试了什么"

**解决方案**：验证矩阵必须与功能目录 1:1 对应，缺测试的功能标注"待补"

---

#### 问题 4：规则/边界（Section 6）与功能 ID 未关联

**现状**：15 条规则没有与功能 ID 建立映射

**示例**：
- `R-006 freshness required` 影响 6 个任务，但没有用 F-* ID 关联
- `R-009 interval 受限` 影响 F-TK-003，但没有标注
- `R-011 商品趋势分类固定四类` 影响 F-CM-003，但没有标注

**影响**：测试工程师拿到功能 ID 时，不知道还要翻 Section 6 找约束

**解决方案**：
1. 在规则表中增加"关联功能"列
2. 或在每个功能规格卡中内联该功能的适用规则

---

### P2 - 中等问题

#### 问题 5：场景（Section 3.3）与功能 ID 断裂

**现状**：S1 ~ S8 描述了 8 个业务场景，但没有与 F-* ID 建立映射

**示例**：
- S4："用户先执行 `fetch_realtime_snapshot`，再执行 `intraday_monitor`" — 这是 F-AS-007 + F-AS-008 的组合场景，但没有标注
- S5："通过 skill / shell / admin 对股票池进行增删改查" — 涉及 F-AS-010 + F-SK-005，但没有标注

**影响**：场景是集成测试的天然来源，不建映射就浪费了这个价值

**解决方案**：每个场景增加"涉及功能"列

---

#### 问题 6：AI Skill 层是"指针"而非"规格"

**现状**：Section 5.5 的 Skill 表只写了"对应能力"，指向底层命令

**问题**：Skill 和底层命令不是同一个东西
- Skill 有自己的参数解析方式（自然语言 → 命令参数）
- Skill 有自己的错误处理行为（对用户的提示语不同于 stderr）
- Skill 有自己的权限约束

**影响**：无法判断 Skill 是"纯透传"还是有独立行为，不知道是否需要独立测试

**解决方案**：明确每个 Skill 是"纯透传"还是有独立行为逻辑，后者需要独立的功能规格卡

---

### P3 - 轻微问题

#### 问题 7：文档定位混乱

**现状**：标题是"还原式评审报告"，但使用目标是"功能列表和边界定义"

**矛盾**：
- **评审报告**的读者是评审人，重点是"发现了什么问题"
- **功能规格**的读者是测试/开发人员，重点是"每个功能怎样工作"

**影响**：测试工程师需要从报告语境中"挖"出功能规格

**解决方案**：拆为两份文档
1. **评审报告**（保留 Section 1, 2, 8, 9, 10, 11, 12）— 面向产品/管理层
2. **功能规格文档**（重构 Section 3, 5, 6）— 面向测试/开发，作为后续测试用例的唯一输入

---

#### 问题 8："状态"列无意义

**现状**：30 个功能全部标注"已实现"，一列全是同一个值

**解决方案**：改为反映**规格完备度**，比如"规格完整 / 规格不完整 / 待拆分"

## 优化优先级总表

| 优先级 | 问题 | 动作 | 工作量估算 |
|---|---|---|---|
| P0 | 功能缺输入/输出/前置/异常规格 | 每个功能扩展为功能规格卡 | 30 功能 × 15 分钟 = 7.5 小时 |
| P0 | 功能粒度不一致 | 拆分粗粒度功能到原子操作级 | 识别 + 拆分 = 3 小时 |
| P1 | 验证矩阵覆盖不全 | 补齐 1:1 映射 | 15 功能 × 10 分钟 = 2.5 小时 |
| P1 | 规则未关联功能 ID | 建立双向映射 | 15 规则 × 5 分钟 = 1.5 小时 |
| P2 | 场景未关联功能 ID | 增加涉及功能列 | 8 场景 × 10 分钟 = 1.5 小时 |
| P2 | AI Skill 缺独立规格 | 明确是透传还是有独立行为 | 8 Skill × 15 分钟 = 2 小时 |
| P3 | 文档定位混乱 | 拆为评审报告 + 功能规格 | 重组文档 = 2 小时 |
| P3 | 状态列无意义 | 改为规格完备度 | 30 功能 × 2 分钟 = 1 小时 |

**总工作量估算**：约 21 小时（3 个工作日）

## 优化后的文档结构

### 文档 1：评审报告（archer-review-report.md）

面向产品/管理层，回答"Archer 做了什么，有什么问题"

```
1. 评审结论摘要
2. 权威来源与边界
8. 产品要求到实现入口追踪矩阵
9. 差异与缺口
10. 最终判断
11. 证据索引
12. 建议的后续动作
```

---

### 文档 2：功能规格文档（archer-feature-spec.md）

面向测试/开发，回答"每个功能怎样工作，如何测试"

```
1. 产品对象定义
   1.1 Goal
   1.2 Role
   1.3 Scenario（增加"涉及功能"列）
   1.4 Constraint
   1.5 Non-goal

2. 功能规格目录
   2.1 统一编排层（每个功能扩展为规格卡）
   2.2 A 股域（拆分粗粒度功能）
   2.3 Token 域
   2.4 商品域
   2.5 AI Skill 层（明确透传/独立行为）

3. 规则与边界目录（增加"关联功能"列）

4. 功能验证矩阵（补齐 1:1 映射）

5. 架构与编排模型（技术实现参考）
```

## 功能规格卡模板

```markdown
### F-XX-XXX 功能名

| 字段 | 内容 |
|---|---|
| 功能 ID | F-XX-XXX |
| 功能名 | 中文名称 |
| 入口 | 命令/Skill/Service/页面 |
| 输入参数 | 参数列表（必填/可选，类型，默认值） |
| 前置条件 | 依赖的数据/功能/环境 |
| 正常输出 | 输出格式、字段、示例 |
| 异常行为 | 错误场景 → 预期行为 |
| 边界值 | 空结果/超限/特殊值的处理 |
| 依赖功能 | F-XX-XXX, F-YY-YYY |
| 验证方式 | 测试文件路径或"待补" |
| 适用规则 | R-XXX, R-YYY |
| 规格完备度 | 完整/不完整/待拆分 |
```

## 实施步骤

### 阶段 1：文档拆分（P3 问题）
1. 创建 `archer-review-report.md`（评审报告）
2. 创建 `archer-feature-spec.md`（功能规格）
3. 将原文档内容按新结构重组

### 阶段 2：功能粒度统一（P0 问题 2）
1. 识别粗粒度功能（F-AS-010, F-AS-014, F-AS-016 等）
2. 拆分为原子操作级功能
3. 重新分配功能 ID

### 阶段 3：功能规格补全（P0 问题 1）
1. 为每个功能创建规格卡
2. 补全输入/输出/前置/异常/边界信息
3. 标注规格完备度

### 阶段 4：关联关系建立（P1 + P2 问题）
1. 补全验证矩阵（功能 → 测试）
2. 建立规则映射（规则 → 功能）
3. 建立场景映射（场景 → 功能）
4. 明确 Skill 行为类型

### 阶段 5：质量检查
1. 确认所有功能都有规格卡
2. 确认所有规则都有关联功能
3. 确认所有场景都有涉及功能
4. 确认验证矩阵 1:1 覆盖

## 验收标准

### 评审报告验收
- [ ] 包含评审结论、差异缺口、后续动作
- [ ] 面向产品/管理层，语言简洁
- [ ] 不包含详细功能规格

### 功能规格文档验收
- [ ] 每个功能都有完整的规格卡
- [ ] 功能粒度统一到"单一可测试行为"
- [ ] 验证矩阵与功能目录 1:1 对应
- [ ] 规则表包含"关联功能"列
- [ ] 场景表包含"涉及功能"列
- [ ] AI Skill 明确行为类型
- [ ] 测试工程师可直接基于此文档编写测试用例

---

## 核心一句话总结

**当前文档能告诉我"Archer 有哪些功能"，但不能告诉我"每个功能该怎么测"。需要从"报告"升级为"规格"。**
