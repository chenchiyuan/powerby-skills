🧭 先明确新的总原则：事实优先、证据优先、时间优先、实现优先

你补充的内容，我建议上升为框架级总原则。  
这几条原则会约束所有模块，不只是资料收集模块。

## 一、框架级总原则

1. 事实还原原则
评审必须基于项目已有事实材料进行还原，不得凭经验脑补、行业常识补齐、理想设计替代现状。

含义
- 只还原项目“已经表达过”的东西
- 未表达的内容可以标记为空缺，但不能擅自补完
- “合理推测”可以存在，但必须明确标记为推断，不得混同为事实
  

---

2. 项目内证据闭环原则
所有对象与关系的建立，必须尽量来源于项目自身材料。

项目自身材料包括
- 产品文档
- 需求文档
- README / Wiki
- 源代码
- 配置文件
- API 文档
- 测试代码
- 提交记录
- Issue / PR 描述
- 架构图
- 日志 / 监控配置
  
不应作为直接事实来源的内容
- 通用行业经验
- 模型自身知识库中的“常见做法”
- 外部产品常识
- 对项目意图的无证据想象
  

---

3. 代码真实状态优先原则
在没有更新、更明确、可信的上游产品/需求事实时，代码代表项目的真实实现状态，应作为最高优先级事实来源。

含义
- 代码是系统“实际运行逻辑”的最强证据
- 文档可能过时，代码通常更接近现状
- 对实现层、架构层、规则层，代码优先级通常最高
  
但要注意
这不是说“代码定义产品”。  
而是说：

- 代码定义真实实现状态
- 产品文档定义目标需求状态
- 两者可能不一致
- 评审要还原这种不一致，而不是替它们自动和解
  

---

4. 产品文档定义需求优先原则
在产品层对象还原时，如果存在明确产品文档，则应优先以产品文档定义产品目标、功能诉求与边界。

含义
- 产品目标不应主要靠代码猜
- 需求状态优先看产品文档
- 如果有多个版本产品文档，应优先采用时间更近、状态更新的文档
  

---

5. 新证据优先原则
当存在多个版本、多个来源、相互冲突的证据时，应优先采用时间更新、状态更明确、上下文更完整的证据。

推荐优先判断维度
1. 时间更近
2. 状态更明确（final / accepted / merged）
3. 来源更权威（正式 PRD > 临时笔记）
4. 与代码/测试一致性更高
  

---

6. 提交记录辅助还原原则
代码提交记录、PR 描述、Issue 讨论可作为产品意图、演进路径和边界变化的辅助证据。

作用
- 补足缺失产品文档
- 识别功能演进过程
- 识别需求变更和实现背景
- 解释为什么代码会呈现某种结构
  

---

7. 缺失显式化原则
无法从已有事实中还原的内容，应明确输出为“缺失”“未找到证据”或“待确认”，而不是隐式补全。

含义
- 缺失信息本身就是评审结果
- “没有证据”也是一种重要事实
  

---

🔍 基于新原则，模块体系需要升级成“证据驱动型模块”

你原来想的是“每个模块单独运行，各自负责一个对象层”。  
现在要再加一个维度：

每个模块不仅要产出对象，还要对对象的证据来源、时间新旧、事实级别负责。

所以模块定义中要增加 3 个共性字段：

- 事实来源
- 证据优先级
- 推断边界

## F1 资料接入与范围定义模块

这个模块是入口模块，负责定义这次评审到底评什么。

模块目标
建立评审上下文，明确项目范围、资料范围和评审边界。

核心职责
- 接入项目原始资料
- 确定评审对象范围
- 标记资料完整度
- 确认评审单位是“整项目”还是“局部能力”
  
主要功能内容
- 接入仓库、文档、配置、测试、PR/Issue
- 识别项目基本类型
- 确定评审边界：
  - 全项目
  - 单服务
  - 单功能链路
  - 单版本
- 生成资料清单
- 标记缺失资料
  
输入
- 仓库地址 / 代码包
- 文档目录
- 配置和测试文件
- 评审任务说明
  
输出
- 项目资料清单
- 评审范围定义
- 资料缺失列表
  
边界
负责
- 定义这次看什么
- 收资料、列清单、定范围
  
不负责
- 理解内容含义
- 判断产品目标
- 推断功能结构
  
设计思想
先界定“观察对象”，再做内容分析。  
避免评审过程中范围不断漂移。

应遵循的原则
- 范围先行原则
- 项目内资料原则
- 缺失显式原则
- 不做内容推断原则

## F2 证据采集与标准化模块

这是证据层的基础模块。

模块目标
把项目内的原始材料统一采集、切分、标准化，供后续模块消费。

核心职责
- 采集所有项目内部证据
- 标准化不同类型证据
- 对证据打元信息标签
  
主要功能内容
- 文档切分
- README / Wiki 解析
- 目录树提取
- API 文档提取
- 测试文件提取
- 配置项提取
- Git 提交记录提取
- PR / Issue 描述提取
  
输入
- 所有项目原始资料
  
输出
- 证据注册表 Evidence Registry
- 标准化证据单元 Evidence Unit 列表
  
证据单元建议字段
字段
说明
evidence_id
唯一 ID
source_type
doc / code / test / config / commit / issue
source_path
来源路径
timestamp
时间
author
作者
summary
摘要

内容片段
version_hint
版本线索

边界
负责
- 做证据对象化
- 统一格式
  
不负责
- 做事实优先级判断
- 做业务解释
  
设计思想
先把“材料世界”变成“证据世界”。

应遵循的原则
- 证据完整采集原则
- 统一格式原则
- 先采集后理解原则
- 项目内部材料唯一原则

## F3 证据排序与冲突决议模块

这是你新原则下的关键模块。

模块目标
在多个来源、多个版本、多个相互冲突的材料中，判定当前有效事实优先级。

核心职责
- 判断证据优先级
- 解决文档冲突
- 解决需求与实现冲突
- 标记“需求事实”和“实现事实”的差异
  
主要功能内容
1. 证据分类
- 产品事实证据
- 架构事实证据
- 实现事实证据
- 验证事实证据
  
2. 优先级判断
- 产品层：新产品文档优先
- 实现层：代码优先
- 架构层：代码结构 / 配置 / 部署优先于旧架构图
- 演进解释：commit / PR 辅助说明
  
3. 冲突决议
- PRD 和代码不一致时：
  - 记录“需求状态”
  - 记录“实现状态”
  - 不自动归一
    
4. 有效事实输出
- current_product_fact
- current_implementation_fact
- unresolved_conflicts
  
输入
- 标准化证据单元
  
输出
- 证据优先级规则结果
- 冲突证据清单
- 当前有效事实集
  
边界
负责
- 决定“当前采用哪条事实”
- 显式保留冲突
  
不负责
- 评价谁对谁错
- 替项目做需求裁决
  
设计思想
不是消灭冲突，而是把冲突结构化地保留下来。  
因为“需求和实现不一致”本身就是评审事实。

应遵循的原则
- 新证据优先原则
- 代码真实状态优先原则
- 产品文档定义需求优先原则
- 冲突保留原则
- 不自动和解原则

## F4 产品事实还原模块

模块目标
基于产品文档与辅助材料，还原产品目标、角色、场景、约束与非目标。

核心职责
- 识别产品目标
- 识别用户角色
- 识别核心场景
- 识别约束与非目标
- 标记需求版本
  
主要功能内容
- 从 PRD / Wiki / 产品说明中提取 Goal
- 从角色描述 / 页面文案 / 权限设计中提取 Role
- 从用户流程 / 场景描述中提取 Scenario
- 从产品说明和版本记录中提取 Constraint / Non-goal
- 在无 PRD 时，辅助使用 commit / issue / 页面信息做保守推断
  
输入
- 产品文档
- README
- Issue / PR
- 页面文案
- 版本说明
  
输出
- Goal Catalog
- Role Catalog
- Scenario Catalog
- Constraint Catalog
- Non-goal Catalog
- Product Version Fact
  
边界
负责
- 还原需求侧定义的产品世界
  
不负责
- 证明实现是否已满足
- 代替功能模块做详细边界定义
  
设计思想
产品层是“需求事实层”，不是“实现事实层”。

应遵循的原则
- 产品文档优先原则
- 新版本优先原则
- 用户与场景中心原则
- 保守推断原则
- 需求与实现分离原则

## F5 功能事实还原模块

这是整个系统最关键的模块之一。

模块目标
基于产品文档、接口、页面、代码、测试，还原项目实际表达出的功能集合、规则、边界和流程。

核心职责
- 识别功能项
- 识别子功能
- 识别业务规则
- 识别功能边界
- 识别主流程和异常流程
- 识别验收条件证据
  
主要功能内容
1. 功能提取
- 从产品文档提功能
- 从页面与路由提功能入口
- 从 API 提功能能力
- 从代码 service / handler / usecase 提功能实现
- 从测试用例提功能行为
  
2. 规则提取
- 从文档规则说明提取
- 从代码 if / guard / validator 中提取
- 从错误码与文案提取
  
3. 边界提取
- in scope
- out of scope
- preconditions
- edge cases
- failure modes
  
4. 流程提取
- 主流程
- 备选流程
- 异常流程
  
5. 版本与冲突标记
- 文档功能
- 已实现功能
- 部分实现功能
- 历史残留功能
  
输入
- 产品事实对象
- API 文档
- 页面与路由
- 代码
- 测试
- 提交记录
  
输出
- Feature Catalog
- Sub-feature Catalog
- Rule Catalog
- Boundary Catalog
- Flow Catalog
- Feature Evidence Matrix
- Feature State Classification
  
边界
负责
- 还原“系统表达了哪些功能能力”
- 还原“这些功能的边界和规则”
  
不负责
- 设计新功能
- 假设隐藏需求
- 给功能打质量分
  
设计思想
功能不是页面名，也不是接口名，而是系统对某种用户目标的能力表达。  
边界也不是“脑补不做什么”，而是从规则、错误路径、范围描述中提取。

应遵循的原则
- 功能事实双源原则：需求材料和实现材料共同参与
- 规则显式化原则
- 边界由证据定义原则
- 异常流程同等重要原则
- 文档/实现差异保留原则
- 不以缺失证据做功能脑补原则

## F6 架构事实还原模块

模块目标
基于代码、配置、部署、接口和架构资料，还原系统的真实组织结构与职责分配。

核心职责
- 识别系统、服务、模块
- 识别领域实体
- 识别依赖关系
- 识别关键机制
- 识别架构决策痕迹
  
主要功能内容
- 从仓库结构提模块
- 从运行配置提服务
- 从 API 和调用关系提协作结构
- 从 schema / model 提实体
- 从中间件、配置和基础设施提技术机制
- 从 ADR / 注释 / commit 提决策背景
  
输入
- 代码
- 配置
- 部署文件
- 架构图
- ADR
- 提交记录
  
输出
- System Catalog
- Module Catalog
- Entity Catalog
- Dependency Graph
- Technical Mechanism Catalog
- Architecture Decision Notes
  
边界
负责
- 还原系统组织事实
  
不负责
- 判断架构好坏
- 替业务定义需求
  
设计思想
架构层要优先反映“真实系统结构”，不能只信旧图纸。  
因此代码、部署和配置在这里往往比 PPT 更诚实。

应遵循的原则
- 真实结构优先原则
- 代码/配置优先原则
- 职责可解释原则
- 静态结构先于主观命名原则
- 文档过时可疑原则

- 代码实现存在，产品文档未声明
- 功能存在，未找到架构支撑
- 功能边界存在，未找到测试证据
- 架构文档存在，代码结构不一致
  
输入
- 对象和关系结果
  
输出
- Difference List
- Gap List
- Orphan Object List
- Unresolved Conflict List
  
边界
负责
- 报差异、报缺口
  
不负责
- 直接定性为 bug / 设计差
- 做主观裁判
  
设计思想
先把“不一致”作为客观事实列出来，而不是立即做价值判断。

应遵循的原则
- 差异事实化原则
- 缺口可见原则
- 先描述后评价原则
- 不自动定责原则

## F11 结果编排与审查输出模块

模块目标
把结构化结果输出给人和系统使用。

核心职责
- 组织对象表和关系表
- 输出审查文档
- 输出差异清单
- 输出证据索引
  
主要功能内容
- Markdown 报告生成
- JSON / YAML 对象导出
- 追踪矩阵导出
- 差异报告导出
- 证据索引导出
  
输入
- 全部模块结果
  
输出
- 项目还原报告
- 追踪矩阵
- 差异与缺口报告
- 对象知识库
  
边界
负责
- 组织输出
  
不负责
- 重新解释事实
- 修改上游对象
  
设计思想
所有输出都应来自统一事实库，避免报告和底层数据不一致。

应遵循的原则
- 同源输出原则
- 证据可追溯原则
- 结构优先原则
- 人机共读原则
