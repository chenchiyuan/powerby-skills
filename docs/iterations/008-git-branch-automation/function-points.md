## 核心功能（P0 - 必须实现）

### FP-001: 自动创建迭代分支

**对应需求**: REQ-001

**功能描述**: 在用户执行 `/powerby-asp` 或 `/powerby.define` 创建新迭代时，系统自动创建对应的 feature 分支，命名格式为 `feature/{迭代编号}-{迭代名称}`，从 develop 分支创建，创建后自动切换到该分支，并将分支信息记录到 `.powerby/iterations.json`。

**验收标准摘要**:
- ✅ 分支命名格式正确：`feature/{id}-{name}`
- ✅ 从 develop 分支创建
- ✅ 创建后自动切换到新分支
- ✅ 分支信息记录到 `.powerby/iterations.json`
- ✅ develop 分支不存在时提示错误
- ✅ 权限不足时提示错误

**关键业务规则**:
- 分支命名格式：`feature/{迭代编号}-{迭代名称}`
- 分支从 develop 分支创建
- 分支创建后自动切换到该分支
- 分支信息记录到 `.powerby/iterations.json`

**依赖**:
- 项目必须是 Git 仓库
- 必须存在 develop 分支
- 用户必须有分支创建权限

---

### FP-002: 追踪分支状态

**对应需求**: REQ-002

**功能描述**: 系统自动追踪每个迭代的分支状态，包括 `active`（活跃）、`merged`（已合并）、`deleted`（已删除）、`deleted_local_only`（仅本地删除）四种状态，状态变更时自动更新 `.powerby/iterations.json`，记录分支创建时间、合并时间和删除时间。

**验收标准摘要**:
- ✅ 分支创建后状态为 `active`
- ✅ 分支合并后状态更新为 `merged`
- ✅ 分支删除后状态更新为 `deleted` 或 `deleted_local_only`
- ✅ 状态变更时记录时间戳

**关键业务规则**:
- 分支状态包括：`active`、`merged`、`deleted`、`deleted_local_only`
- 状态变更时自动更新 `.powerby/iterations.json`
- 记录分支创建时间和合并时间

**依赖**:
- FP-001 已实现

---

### FP-003: 自动合并迭代分支

**对应需求**: REQ-003

**功能描述**: 在迭代完成（P8阶段）时，系统提示用户合并 feature 分支到 develop 分支，使用 `git merge --no-ff` 保留提交历史，合并成功后更新分支状态为 `merged`，合并失败时提供清晰的错误信息和解决建议。

**验收标准摘要**:
- ✅ P8 阶段提示用户合并分支
- ✅ 使用 `git merge --no-ff` 保留提交历史
- ✅ 合并成功后更新分支状态为 `merged`
- ✅ 合并失败时提供错误信息和解决建议

**关键业务规则**:
- 合并目标为 develop 分支
- 使用 `git merge --no-ff` 保留提交历史
- 合并成功后更新分支状态为 `merged`
- 合并失败时提供清晰的错误信息和解决建议

**依赖**:
- FP-001 已实现
- FP-002 已实现
- P8 阶段已完成

### FP-004: 清理已合并分支

**对应需求**: REQ-004

**功能描述**: 在分支合并后，系统询问用户是否删除 feature 分支，用户确认后删除本地和远程分支（如果远程分支存在），删除成功后更新分支状态为 `deleted`，用户选择保留时状态保持为 `merged`，远程分支删除失败时本地分支仍删除，状态更新为 `deleted_local_only`。

**验收标准摘要**:
- ✅ 合并后询问用户是否删除分支
- ✅ 用户确认后删除本地和远程分支（如果存在）
- ✅ 删除成功后更新分支状态为 `deleted`
- ✅ 远程分支删除失败时状态更新为 `deleted_local_only`
- ✅ 远程分支不存在时仅删除本地分支
- ✅ 用户选择保留时状态保持为 `merged`

**关键业务规则**:
- 合并完成后询问用户是否删除 feature 分支
- 用户确认后删除本地和远程分支（如果远程分支存在）
- 删除成功后更新分支状态为 `deleted`
- 用户选择保留时状态保持为 `merged`
- 远程分支删除失败时，本地分支仍删除，状态更新为 `deleted_local_only`

**依赖**:
- FP-003 已实现

### FP-005: 检查分支状态

**对应需求**: REQ-005

**功能描述**: 系统在关键节点自动检查 Git 分支状态，P1 开始时检查是否在正确的 feature 分支上，P6 开始时检查是否有未提交的更改，P8 开始时检查是否与远程分支同步（如果远程分支存在），远程分支不存在时跳过同步检查，仅提示用户可选择推送，检查失败时提供清晰的提示和修复建议，检查通过后才允许继续执行后续流程。

**验收标准摘要**:
- ✅ P1 开始时检查当前分支
- ✅ P6 开始时检查未提交的更改
- ✅ P8 开始时检查远程同步状态（如果远程分支存在）
- ✅ 远程分支不存在时跳过同步检查
- ✅ 检查失败时提供提示和修复建议
- ✅ 检查通过后才允许继续执行后续流程

**关键业务规则**:
- P1 开始时检查是否在正确的 feature 分支上
- P6 开始时检查是否有未提交的更改
- P8 开始时检查是否与远程分支同步（如果远程分支存在）
- 远程分支不存在时跳过同步检查，仅提示用户可选择推送
- 检查失败时提供清晰的提示和修复建议
- 检查通过后才允许继续执行后续流程

### FP-007: 检测合并冲突

**对应需求**: REQ-007

**功能描述**: 在合并前系统自动检测是否存在冲突，执行 `git merge --no-commit --no-ff` 进行预检测，存在冲突时列出冲突文件清单并执行 `git merge --abort` 清理现场，提供冲突解决指南，用户手动解决冲突后可重新触发合并流程，无冲突时执行 `git merge --abort` 回滚预检测，然后执行正式合并。

**验收标准摘要**:
- ✅ 合并前执行 `git merge --no-commit --no-ff` 预检测
- ✅ 检测到冲突时执行 `git merge --abort` 清理现场
- ✅ 列出冲突文件清单
- ✅ 提供冲突解决指南
- ✅ 无冲突时执行 `git merge --abort` 回滚预检测，然后执行正式合并
- ✅ 用户手动解决冲突后可重新触发合并流程

**关键业务规则**:
- 合并前执行 `git merge --no-commit --no-ff` 检测冲突
- 存在冲突时列出冲突文件清单，并执行 `git merge --abort` 清理现场
- 提供冲突解决指南
- 用户手动解决冲突后，可重新触发合并流程
- 无冲突时执行 `git merge --abort` 回滚预检测，然后执行正式合并

**依赖**:
- FP-003 已实现
