# PowerBy Bugfix

证据驱动的 Bug 诊断与修复。通过三层立体诊断定位根因，以最小代价修复问题，单文档记录完整过程。

## Purpose

快速、准确地定位和修复代码中的问题。成功使用的标志是：根因定位有证据支撑，修复方案影响面最小，修复后问题不复现且无新回归。

## Success criteria

- 根因分析基于日志、堆栈、代码逻辑等显式证据，不基于猜测
- 修复方案通过复现测试、回归测试和边界测试
- 完整的修复文档已归档（问题描述、证据链、根因、修复方案、验证结果）
- 临时文件已清理
- 失败时：记录已排除的方向和剩余假设，供后续接手

## Strategy

1. **证据驱动，拒绝猜测。** 所有推论必须基于错误日志、堆栈信息或代码逻辑的必然性。"我觉得"、"可能"不是诊断依据。当证据不足时，设计实验获取新证据，而不是基于假设直接修复。

2. **三层立体诊断。** 将问题空间分为表现层（UI/交互/响应）、逻辑层（业务逻辑/算法）、数据层（存储/传输/完整性）。每层独立诊断，再做跨层联动验证，构建正向证据链和反向排除链。

3. **最小代价修复。** 在确保修复彻底且不产生回归的前提下，选择影响面最小的方案。不改变系统架构，只在问题范围内修复。

4. **需求对齐先于诊断。** 先查找 PRD 或需求文档确认"正确行为"的定义，再判断当前行为是否偏离。避免把"设计如此"的行为误判为 Bug。

5. **单文档闭环记录。** 从问题报告到验证通过，全过程在一个文档中完成，形成可复用的诊断经验。

## Tools and capability boundaries

- **文件系统读写**：读取代码、日志、配置；写入 Bug 文档和临时分析脚本
- **命令行工具**：运行测试、查看日志、执行分析脚本
- **不做**：大规模代码重构或新功能开发
- **不做**：Git 分支管理 —— 由 powerby-github-branch 根据 Bug 级别创建对应分支

## Important facts and constraints

### 文档路径

- 全局 Bug：`docs/bugs/global/bug-{id}-{标识}.md`
- 迭代 Bug：`docs/{project}/bugs/bug-{id}-{标识}.md`
- 临时文件：`temp_scripts/`（analysis/、validation/、mock/、logs/）

### Bug 严重程度与分支策略

| 级别 | 分支类型 | 源分支 | 合并目标 |
|------|---------|--------|---------|
| P0/P1 | hotfix | main | main + develop |
| P2/P3 | bugfix | develop | develop |

### 模板资源

- `assets/bug-report-template.md` — 问题报告模板
- `assets/rca-template.md` — 根因分析模板
- `assets/fix-plan-template.md` — 修复方案模板

### 临时文件必须清理

修复完成后 `temp_scripts/` 目录必须清空。临时分析脚本、验证数据、模拟数据都不进入最终提交。

## Workflow

1. **问题报告** — 查找 PRD 对齐需求理解，创建 Bug 文档，记录问题描述、复现步骤、证据（日志/堆栈/截图）、影响评估。

2. **三层诊断** — 表现层、逻辑层、数据层逐层分析。每层产出：代码分析 + 表现分析 + 验证结论。跨层联动验证构建证据链。

3. **方案设计** — 生成至少 2 个备选方案，评估优缺点、风险和成本，标记推荐方案。工作量 >2 小时或涉及多模块时必须经过用户确认。

4. **实施修复** — 按确认方案执行修复，记录每处变更。

5. **验证测试** — 复现测试（原问题已修复）、回归测试（无新问题）、边界测试（边界条件正常）。

6. **交付归档** — 完善 Bug 文档，清理 `temp_scripts/`，提交最终报告。

## Output format

Bug 文档结构（单文档）：

```markdown
# Bug-{id}: {问题标题}

## 问题报告
- 描述 / 复现步骤 / 证据 / 影响评估

## 诊断分析
- 表现层 / 逻辑层 / 数据层 / 跨层验证 / 证据链

## 修复方案
- 方案 A / 方案 B / 推荐方案及理由

## 修复记录
- 变更明细 / 代码修改列表

## 验证结果
- 复现测试 / 回归测试 / 边界测试

## 状态: {已修复/待确认/未解决}
```

## Subtask / parallelism guidance

- 三层诊断可并行进行，各层独立分析后再汇总联动验证
- 当问题明确定位到单层时，跳过其他层的深入分析

## Examples

**Example 1: 登录超时问题**
Input: "用户登录偶尔超时，日志显示数据库连接池耗尽"
Output: 数据层诊断发现连接泄漏 -> 定位到未关闭的数据库连接 -> 最小修复添加连接释放 -> 验证通过。

**Example 2: 显示异常**
Input: "页面数据显示为空，但数据库有数据"
Output: 表现层正常渲染 -> 逻辑层 API 返回空数组 -> 数据层查询条件错误 -> 修复查询逻辑。

## Safety

- 不基于猜测直接修复，必须有证据支撑
- 不改变系统整体架构，只在问题范围内修复
- 不静默吞掉异常或用默认值掩盖错误
- 不在未验证的情况下标记 Bug 为已修复
- 修复完成后必须清理所有临时文件
