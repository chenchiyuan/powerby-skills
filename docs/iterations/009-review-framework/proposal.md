# Proposal: 还原式项目评审框架（Review Framework）

## 1. 产品定位

- **目标用户**：技术 Leader、架构师、开发团队、外部审计方、AI Agent
- **核心价值**：系统性地识别需求-实现偏差，防止项目方向失控，通过清晰定义的标准和方法进行可量化、可追溯的事实还原
- **成功指标**：
  - 能够生成完整的可追溯证据链，支持审计
  - 能够识别需求-设计-实现不一致的地方
  - 基于标准/方法进行还原，输出可量化、可追溯的结果

## 2. 需求清单

| ID | 需求描述 | 优先级 | 验收标准（草案） |
|----|---------|--------|----------------|
| REQ-001 | 定义统一的 Skill 协议，规范输入输出格式 | 必须 | 所有 Skill 遵循统一协议，可独立运行和编排协作 |
| REQ-002 | 设计证据驱动的数据模型（Evidence Unit、Object Record 等） | 必须 | 所有对象都有证据来源，可追溯 |
| REQ-003 | 实现证据优先级与冲突决议机制 | 必须 | 能识别新旧文档冲突、文档与代码冲突，显式保留差异 |
| REQ-004 | 实现产品事实还原（Goal、Role、Scenario） | 必须 | 从 PRD/README 提取产品对象，输出 Catalog |
| REQ-005 | 实现功能事实还原（Feature、Rule、Boundary） | 必须 | 从文档/API/代码/测试提取功能对象，输出 Catalog |
| REQ-006 | 实现关系构建（Goal → Feature 追踪） | 必须 | 建立跨层追踪关系，输出 Traceability Matrix |
| REQ-007 | 实现差异与缺口识别 | 必须 | 识别需求-实现偏差、对象缺失、链路断点 |
| REQ-008 | 实现项目接入与范围定义 | 必须 | 接入项目资料，定义评审范围，生成资料清单 |
| REQ-009 | 实现证据采集与标准化 | 必须 | 采集项目内证据，标准化为 Evidence Unit |
| REQ-010 | 实现报告编排与导出（Markdown） | 必须 | 生成人类可读的 Markdown 报告 |
| REQ-011 | 实现架构事实还原（Module、Entity、Dependency） | 应该 | V2 阶段实现，从代码结构提取架构对象 |
| REQ-012 | 实现实现事实还原（Code Unit、Entry Point） | 应该 | V2 阶段实现，识别代码单元和入口点 |
| REQ-013 | 实现验证事实还原（Test、Observability） | 应该 | V2 阶段实现，识别测试和监控对象 |

## 3. 明确排除

| ID | 排除项 | 排除理由 |
|----|--------|---------|
| EXC-001 | 自动修复代码问题 | 框架只做还原和识别，不做修复 |
| EXC-002 | 生成新的需求文档 | 框架基于已有材料，不创造新内容 |
| EXC-003 | 代码质量打分（A/B/C 评级） | 框架输出事实和差异，不做主观评价 |
| EXC-004 | 性能分析、安全扫描 | 超出还原式评审范围 |
| EXC-005 | 项目管理功能 | 不做任务分配、进度跟踪 |

## 4. 约束条件

| ID | 约束描述 |
|----|---------|
| CON-001 | 必须基于 Claude Skill 协议实现 |
| CON-002 | 必须遵循"事实优先、证据优先"原则 |
| CON-003 | 代码是实现层最高优先级事实来源 |
| CON-004 | 新产品文档优先于旧文档 |
| CON-005 | 需求与实现不一致时，显式保留差异，不自动和解 |
| CON-006 | 没有证据时输出"缺失/待确认"，不脑补 |
| CON-007 | V1 优先跑通"产品 → 功能 → 关系 → 差异"主链路 |
| CON-008 | 输出格式为 Markdown 文档（人类可读） |
