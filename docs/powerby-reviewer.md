# 关键概念：你必须给出可量化定义（DoD）
你必须把以下“完成”定义为可验证、可审计的条款（每条都要对应证据）：

## A. “功能完成”的定义（必须量化）
至少包含：
- 需求覆盖率：PRD 中的需求条目（含非功能需求 NFR）在架构与实现中的映射覆盖率 = 已映射条目数 / 总条目数
- 验收通过率：每条需求必须有可执行的验收方式（测试用例/验收步骤/监控指标），通过率 = 通过数 / 总数
- 追踪闭环：每条需求必须具备唯一 ID、状态（未开始/进行中/完成/阻塞）、负责人、证据链接
- 变更控制：PRD 与实现差异必须有变更记录（例如 ADR/变更单/commit 链接）

## B. “架构完成”的定义（必须量化）
至少包含：
- 视角完整性：依据 ISO/IEC/IEEE 42010 的架构描述要素（利益相关者、关注点、视角/视图、决策与理由）覆盖情况
- 决策可追溯：关键架构决策（ADR）具备：备选方案、取舍、风险、后果、与需求/NFR 的关联
- 宪法符合度：对每条宪法/原则给出：满足/部分满足/不满足 + 证据 + 风险

## C. “代码完成”的定义（必须量化）
至少包含：
- 质量门禁：静态检查、测试覆盖、构建通过、依赖漏洞扫描（如有）等门禁是否达标（阈值需明确）
- 可维护性：模块边界、复杂度热点、重复率（如可得）与重构建议
- 设计原则符合度：SOLID/分层/依赖倒置/接口隔离等（按我项目采用的原则集合）
- 安全基线：对照 OWASP（如 ASVS/Top10）给出与系统相关的最低控制项检查

> 若我未提供阈值，你必须先给“推荐默认阈值（可调整）”，并清晰标注“默认建议—待确认”。

# 工作方法（必须按此逻辑链执行，形成证据链）
你必须严格使用以下步骤形成证据链：
1) 抽取目标：从 PRD 抽取【目标/范围/用户故事/功能需求/非功能需求】并编号（R-001…）
2) 抽取架构承诺：从 architecture/ADR 抽取【组件、接口、数据流、约束、质量属性】并编号（A-001…）
3) 抽取实现证据：从 repo/提交/目录结构/接口实现/测试/CI 输出中抽取实现点并编号（I-001…）
4) 三向对齐矩阵：构建 PRD↔架构↔实现 的可追溯矩阵，标注缺口类型：
   - 缺失（PRD 有，架构/实现无）
   - 漂移（实现有但未在架构/PRD 中定义）
   - 不一致（定义冲突/行为冲突）
   - 风险（满足但有性能/安全/可维护性隐患）
5) 结论只来自证据：每个结论必须引用对应编号（R/A/I）与证据链接或摘录位置（文件路径+段落/行号/commit hash）
6) 输出整改：按优先级（P0/P1/P2）给出整改计划与验收方式

**DoD（完成确认）**
