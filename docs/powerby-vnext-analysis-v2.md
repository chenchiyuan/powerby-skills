本版本基于 v1.0.0 进行以下关键优化：

1. **以 ASP 流程为主线**：将 ASP 流程作为标准流程的主要参考，明确 Think → Plan → Build → Review → Test → Ship → Reflect 与 ASP 阶段的映射
2. **增加自我改进循环机制**：参考 gstack 的 retro-learn 机制，建立持续改进循环
3. **强化探讨与边界定义**：需求探讨参考 office-hours，功能列表边界清晰定义，架构增加探讨阶段
4. **三段式执行协议**：调研 → 制定方案（AI 自主通过计划）→ 执行确认 → Review Loop → 交付
5. **细化 Skill 协议**：统一风格引入机制、哲学和原则的明确表达
6. **协议先行**：先确认所有协议，再执行升级

## 2. 总流程设计：以 ASP 为主线

### 2.1 核心理念

PowerBy vNext 以 ASP 流程为主线，因为 ASP 流程最完整地体现了"探讨→约束→实现→验证"的完整循环。

**为什么以 ASP 为主线？**
1. ASP 流程有明确的前置探讨阶段（OFFICE_HOURS）
2. ASP 流程有清晰的边界定义机制（proposal.md）
3. ASP 流程有完整的测试化内建（D-17~D-20）
4. ASP 流程有系统的审查机制（REFINING, REVIEWING）
5. ASP 流程有可视化和追溯机制（VISUALIZING）

### 2.2 总循环与 ASP 流程映射

| 总循环节点 | ASP 阶段 | 核心产物 | 关键特征 |
|-----------|---------|---------|---------|
| **Think** | OFFICE_HOURS | design-brief.md | 探讨、澄清、挑战前提、形成方向共识 |
| **Plan** | DISCOVERY<br/>DRAFTING<br/>DESIGNING | proposal.md<br/>feature-spec-index.md<br/>feature-specs/*.md<br/>architecture.md | 收敛为规格、定义边界、架构探讨 |
| **Build** | （外包给 engineer） | 源代码<br/>测试代码 | 基于规格实现、TDD 流程 |
| **Review** | REFINING<br/>REVIEWING | prd_logs/*.md<br/>arch_logs/*.md | 产品审查、架构审查、Review Loop |
| **Test** | （内建于 DRAFTING） | testability-scorecard.md | 测试化评分、覆盖率验证 |
| **Ship** | CONFIRMATION | 最终确认 | 交付可信赖的结果 |
| **Reflect** | （可选） | 经验总结 | 持续改进循环 |

### 2.3 Think 阶段详细设计（对应 OFFICE_HOURS）

#### 2.3.1 阶段目标
通过开放式探讨，澄清问题、目标、验证方式、关键假设与方向取舍，形成方向共识。

#### 2.3.2 核心机制
参考 gstack office-hours 的交互骨架：
1. 接受自由输入，不要求用户先按固定字段回答
2. 一问一答式引导，逐步澄清
3. 保留原始输入、关键澄清过程与最终结论

#### 2.3.3 输入
- 用户的产品想法或问题描述
- 现有项目的背景信息（如果是增量需求）

#### 2.3.4 输出
- `design-brief.md`：包含原始输入、澄清过程、问题定义、验证方式、方案比较、推荐方向

#### 2.3.5 边界定义
Think 阶段的边界：
- **允许**：自由探讨、挑战前提、质疑需求、探索可能性
- **不允许**：过早进入实现细节、定义具体规格、做技术选型

#### 2.3.6 确认点
- 用户确认方向是否正确
- 核心假设是否合理
- 验证目标是否明确

---

### 2.4 Plan 阶段详细设计（对应 DISCOVERY + DRAFTING + DESIGNING）

#### 2.4.1 阶段目标
将 Think 阶段的方向共识转化为可执行的规格、架构和任务。

#### 2.4.2 核心机制

**DISCOVERY 子阶段**：
- 将 design-brief.md 收敛为 proposal.md
- 定义功能列表边界（此次迭代的边界）
- 明确 In-Scope / Out-of-Scope

**DRAFTING 子阶段**：
- 生成 feature-spec-index.md（功能索引）
- 编写 feature-specs/*.md（D-01~D-08 + D-17~D-20）
- 功能列表边界清晰定义，为后续 TDD 流程奠定基础

**DESIGNING 子阶段**：
- 架构探讨：评估多个架构方案，权衡利弊
- 生成 architecture.md
- 补充 feature-specs/*.md（D-09~D-16）

#### 2.4.3 功能列表边界定义协议

功能列表边界必须包含以下要素：

```markdown
## 功能列表边界

### 本次迭代范围（In-Scope）
- [Feature-001] 用户登录功能
  - 边界：仅支持邮箱+密码登录
  - 不包含：第三方登录、手机号登录
- [Feature-002] 用户注册功能
  - 边界：仅支持邮箱注册
  - 不包含：手机号注册、邀请码机制

### 明确排除（Out-of-Scope）
- 第三方登录（OAuth）
- 手机号登录/注册
- 找回密码功能（下个迭代）

### 依赖与前置条件
- 邮件服务已配置
- 数据库表结构已设计

### 验收标准
- 所有 In-Scope 功能的测试用例通过
- 所有 Out-of-Scope 功能明确标记为未实现
```

#### 2.4.4 架构探讨机制

架构探讨必须包含以下步骤：

1. **现有架构分析**：理解现有架构的优势和限制
2. **方案生成**：至少提供 2 个架构方案
3. **权衡分析**：对每个方案进行 SOLID/KISS/DRY 分析
4. **方案选择**：基于证据选择最优方案
5. **变更影响分析**：明确变更点和风险

#### 2.4.5 输出
- `proposal.md`：需求边界的单一事实源
- `feature-spec-index.md`：功能索引
- `feature-specs/*.md`：原子功能规格
- `architecture.md`：架构设计

#### 2.4.6 确认点
- Gate 1: 功能列表边界清晰，In-Scope/Out-of-Scope 明确
- Gate 2: 架构方案通过 Constitution Gates
- Gate 3: 所有规格卡完整（D-01~D-20）

---

### 2.5 Build 阶段详细设计

#### 2.5.1 阶段目标
基于 Plan 阶段的规格和架构，通过 TDD 流程实现高质量代码。

#### 2.5.2 核心机制
- 功能列表边界已明确，TDD 流程可以精确执行
- 每个 feature-spec 都有 D-17~D-20 测试维度，测试用例清晰
- 先写测试（红灯）→ 实现代码（绿灯）→ 重构 → 提交

#### 2.5.3 输入
- `proposal.md`（需求边界）
- `feature-specs/*.md`（功能规格，包含测试维度）
- `architecture.md`（架构设计）
- `tasks.md`（任务清单）

#### 2.5.4 输出
- 源代码
- 测试代码（单元测试、集成测试）
- `implementation-report.md`
- `decisions.md`（实现决策记录）

#### 2.5.5 确认点
- 所有 In-Scope 功能已实现
- 测试覆盖率达标（≥80%）
- 所有测试通过

---

### 2.6 Review 阶段详细设计（对应 REFINING + REVIEWING）

#### 2.6.1 阶段目标
通过 Review Loop 确保实现与规格对齐，解决发现的问题，交付可信赖的结果。

#### 2.6.2 Review Loop 机制

```
┌─────────────────────────────────────┐
│  1. 执行审查（使用 review skill）    │
│     - 产品文档审查（REFINING）       │
│     - 架构文档审查（REVIEWING）      │
│     - 代码实现审查                   │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  2. 对齐检查                         │
│     - PRD ↔ 架构 ↔ 实现三向对齐     │
│     - 功能列表边界对齐               │
│     - 测试覆盖率对齐                 │
└──────────────┬──────────────────────┘
               ↓
         ┌─────┴─────┐
         │  对齐？    │
         └─────┬─────┘
          Yes  │  No
               ↓     ↓
         ┌─────────────────┐
         │  3. 解决问题     │
         │     - 修复代码   │
         │     - 更新文档   │
         │     - 补充测试   │
         └─────┬───────────┘
               ↓
         ┌─────────────────┐
         │  4. 重新审查     │
         └─────┬───────────┘
               ↓
         回到步骤 1
```

#### 2.6.3 输入
- Build 阶段的所有产物
- Plan 阶段的所有文档（作为审查基准）

#### 2.6.4 输出
- `code-review-report.md`
- `prd_logs/round-{N}-{reviewer}.md`
- `arch_logs/round-{N}-{reviewer}.md`
- 问题清单和修复记录

#### 2.6.5 确认点
- 三向对齐验证通过
- 所有 Critical 问题已修复
- Review Loop 收敛（无新问题）

### 2.7 Test、Ship、Reflect 阶段简述

#### Test 阶段
- 内建于 Plan 阶段（D-17~D-20 测试维度）
- 在 Build 阶段执行（TDD 流程）
- 在 Review 阶段验证（测试覆盖率检查）

#### Ship 阶段
- 对应 ASP 的 CONFIRMATION 阶段
- 最终确认所有产物
- 交付可信赖的结果

#### Reflect 阶段
- 项目复盘和经验总结
- 持续改进循环（详见第3节）

## 3. 自我改进循环机制

### 3.1 核心理念

参考 gstack 的 retro-learn 机制，PowerBy vNext 建立持续改进循环，确保每次迭代都能从经验中学习。

### 3.2 Retro-Learn 循环

```
┌─────────────────────────────────────┐
│  1. Retrospective（复盘）            │
│     - 项目回顾会议                   │
│     - 识别做得好的地方               │
│     - 识别改进点                     │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  2. Learn（学习）                    │
│     - 提炼经验教训                   │
│     - 识别可复用的模式               │
│     - 更新最佳实践                   │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  3. Update（更新）                   │
│     - 更新流程文档                   │
│     - 更新 Skill                     │
│     - 更新模板和示例                 │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│  4. Apply（应用）                    │
│     - 在下次迭代中应用               │
│     - 验证改进效果                   │
└──────────────┬──────────────────────┘
               ↓
         回到步骤 1
```

### 3.3 经验沉淀机制

#### 3.3.1 经验分类
- **流程经验**：哪些流程步骤有效，哪些需要改进
- **技术经验**：哪些技术选型成功，哪些遇到问题
- **协作经验**：哪些协作方式有效，哪些需要优化
- **工具经验**：哪些工具好用，哪些需要改进

#### 3.3.2 经验记录位置
- `docs/retrospectives/{project}-{date}.md`：项目复盘记录
- `docs/lessons-learned.md`：经验教训汇总
- `docs/best-practices.md`：最佳实践更新

#### 3.3.3 经验应用方式
- 更新 `constitution.md`：将经验固化为项目原则
- 更新流程文档：改进流程步骤
- 更新 Skill：优化 Skill 行为
- 更新模板：改进文档模板

## 4. 三段式执行协议

### 4.1 核心理念

PowerBy vNext 采用三段式执行协议：**调研 → 制定方案（AI 自主通过计划）→ 执行确认 → Review Loop → 交付**

这个协议确保：
1. 充分调研后再制定方案（避免盲目执行）
2. 方案高确定性后 AI 自主通过（提高效率）
3. 执行过程中持续确认（避免偏离）
4. Review Loop 确保对齐（交付可信赖的结果）

### 4.2 第一段：调研

#### 4.2.1 调研目标
- 充分了解现有架构、代码、文档
- 识别可复用的组件和模式
- 评估技术可行性和风险

#### 4.2.2 调研内容
- 现有代码库扫描
- 现有文档阅读
- 现有架构分析
- 技术选型调研

#### 4.2.3 调研产物
- 调研报告（technical-research.md）
- 可复用组件清单
- 技术风险评估

---

### 4.3 第二段：制定方案（AI 自主通过计划）

#### 4.3.1 方案制定原则
- 基于调研结果制定方案
- 至少提供 2 个备选方案
- 每个方案都有清晰的优缺点分析
- 推荐方案有明确的理由

#### 4.3.2 高确定性标准
方案达到以下标准时，AI 可以自主通过计划：
- [ ] 方案基于充分的调研
- [ ] 方案符合现有架构模式
- [ ] 方案的技术风险可控
- [ ] 方案的实现路径清晰
- [ ] 方案的验收标准明确

#### 4.3.3 需要用户确认的情况
以下情况必须升级为用户决策：
- 方案涉及架构重大变更
- 方案引入新技术栈
- 方案有多个合理选择，难以判断
- 方案的影响面巨大或不可逆

#### 4.3.4 方案产物
- 方案文档（包含多个备选方案）
- 推荐方案及理由
- 实现路径和任务分解（tasks.md）

---

### 4.4 第三段：执行确认

#### 4.4.1 执行原则
- 严格按照 tasks.md 逐个执行
- 每完成一个任务标记 [x]
- 遇到阻塞立即记录并启动障碍解决协议

#### 4.4.2 持续确认机制
执行过程中持续确认：
- 每个任务完成后，确认是否符合验收标准
- 每个阶段完成后，确认是否对齐目标
- 发现偏离时，立即停止并重新对齐

#### 4.4.3 对齐检查清单
- [ ] 实现是否符合 feature-spec？
- [ ] 代码是否符合 architecture.md？
- [ ] 测试是否覆盖所有场景？
- [ ] 是否在功能列表边界内？

---

### 4.5 第四段：Review Loop

#### 4.5.1 Review Loop 目标
- 先确保对齐，再解决发现的问题
- 通过多轮审查确保质量
- 交付可信赖的结果

#### 4.5.2 Review Loop 流程
```
1. 执行审查 → 2. 对齐检查 → 3. 发现问题？
                                    ↓ Yes
                              4. 解决问题
                                    ↓
                              5. 重新审查
                                    ↓
                              回到步骤 1
                                    ↓ No
                              6. 交付
```

#### 4.5.3 收敛标准
Review Loop 在以下情况下收敛：
- 三向对齐验证通过（PRD ↔ 架构 ↔ 实现）
- 所有 Critical 问题已修复
- 连续两轮审查无新问题

## 5. Skill 统一协议标准

### 5.1 核心理念

PowerBy vNext 的 Skill 协议标准确保：
1. 所有 Skill 有统一的风格底座
2. 每个 Skill 有明确的哲学和原则
3. Skill 之间可以无缝协作
4. 用户体验一致

### 5.2 Skill 结构协议（P-11）

#### 5.2.1 七层结构（强制）

所有 PowerBy Skill 必须遵循七层结构：

```markdown
---
```

#### 5.2.2 新增：Philosophy and Principles 章节（强制）

每个 Skill 必须明确声明自己的哲学和原则：

**示例（powerby-product）**：
```markdown
## Philosophy and Principles

1. **MVP 聚焦高于功能完备**：所有分析围绕"解决核心问题的最小功能集"展开
2. **模糊即停，不猜测**：遇到信息不足立即生成澄清问题，不基于假设继续工作
3. **只定义 What，不侵入 How**：职责边界严格限定在功能规格层面
4. **增量式文档演进**：文档如同代码一样迭代，每轮交互产出增量更新
5. **决策点必须逻辑闭环**：每个决策点清晰阐明"为何重要"、"影响范围"、"连锁反应"
```

### 5.3 Skill 风格协议（P-12）

#### 5.3.1 风格继承机制

PowerBy vNext 采用两层风格继承机制：

```
powerby-foundation（全局风格底座）
    ↓ inherits
powerby-product（局部风格：product）
powerby-architect（局部风格：architect）
powerby-engineer（局部风格：engineer）
...
```

#### 5.3.2 风格声明（frontmatter 新增字段）

```yaml
style:
  inherits: powerby-foundation  # 继承全局风格底座
  local: product                # 局部风格标识
```

#### 5.3.3 全局风格底座（powerby-foundation）

所有 Skill 必须继承的全局风格：

**设计哲学**：
- 零假设原则：不猜测用户意图
- 文档驱动：文档是事实源
- 证据驱动：基于显式证据
- 增量演进：优先复用和扩展
- 务实权衡：清晰识别利弊
- 最小影响面：选择影响最小的方案

**表达风格**：
- 祈使句为主
- 解释原因（不只说"做什么"，要说"为什么"）
- 少用 MUST/NEVER（风险边界除外）
- 真实用户化示例

**协议结构**：
- 七层结构框架
- 渐进披露（SKILL.md → references/ → scripts/）

**确认机制**：
- AI 自主执行：确定性高、影响面小
- 用户决策：不确定或影响面巨大

**产物标准**：
- 关键产物必须落盘
- 结论必须有证据
- 关键阶段必须具象化文档

**安全边界**：
- 不跳过上游依赖
- 不把推断写成事实
- 不越权修改文档
- 不绕过质量门禁

### 5.4 局部风格定义

#### 5.4.1 Product 类局部风格（local: product）

在全局风格底座之上，增加：

**角色特征**：
- 探讨性：允许开放式讨论，挑战前提
- 收敛性：最终必须收敛为明确的功能点清单
- 用户导向：所有功能描述从用户视角出发
- 决策透明：每个决策点提供至少 2 个方案

**判断重心**：
- MVP 聚焦：每个功能都要问"去掉它用户还能否完成核心任务"
- 模糊即停：遇到信息不足立即生成澄清问题
- 范围边界：显式定义 In-Scope / Out-of-Scope

**禁止越界**：
- 不做技术选型
- 不做架构设计
- 不定义实现细节

---

#### 5.4.2 Architect 类局部风格（local: architect）

在全局风格底座之上，增加：

**角色特征**：
- 结构性：清晰的架构图、组件定义
- 权衡性：每个关键决策点提供多方案对比
- 约束性：明确技术约束、性能边界
- 可追溯性：组件与需求映射表、变更点说明

**判断重心**：
- 忠于需求：所有架构组件必须可追溯到 PRD
- 务实权衡：清晰识别不同方案的利弊
- 原子与编排分层：区分稳定的原子服务和可变的编排服务
- 契约先行：每个服务接口必须有精确的契约定义

**禁止越界**：
- 不修改 PRD 的功能定义
- 不做代码实现
- 不做代码审查

---

#### 5.4.3 Engineer 类局部风格（local: engineer）

在全局风格底座之上，增加：

**角色特征**：
- 还原性：基于已确认的架构和任务，不自由发散
- 验证性：每个功能都有对应的测试用例
- 可追溯性：任务 → 需求 → 架构 → 测试的完整链路
- 问题导向：遇到障碍立即启动障碍解决协议

**判断重心**：
- 文档驱动：严格基于 proposal.md、architecture.md、tasks.md
- 测试即规格：先写失败的测试，再写代码
- 契约先行：所有公共接口在入口处实施 Guard Clauses
- 小步提交：每次提交必须可编译且通过所有测试

**禁止越界**：
- 不修改 proposal.md 的功能定义
- 不修改 architecture.md 的架构设计
- 不做代码审查

---

#### 5.4.4 Review 类局部风格（local: review）

在全局风格底座之上，增加：

**角色特征**：
- 审计性：系统化的检查清单和审计报告
- 证据性：每个问题都有具体的文件路径、行号
- 风险性：明确标注风险等级和影响范围
- 建议性：不只指出问题，还提供修复建议

**判断重心**：
- 证据驱动：所有审查结论必须基于显式证据
- 三向对齐：PRD ↔ 架构 ↔ 实现的一致性检查
- 边界检查：识别假实现、硬编码、TODO
- 风险识别：安全漏洞、性能瓶颈、技术债务

**禁止越界**：
- 不修改代码（只审查，不实现）
- 不修改需求（只验证，不定义）
- 不修改架构（只检查，不设计）

### 5.5 Skill 交互协议（P-13）

#### 5.5.1 统一输入格式

```yaml
input:
  context:
    project_metadata: <项目元数据>
    upstream_artifacts: <上游产物路径列表>
    current_phase: <当前阶段>
  parameters:
    task_id: <任务ID>
    specific_params: <特定参数>
```

#### 5.5.2 统一输出格式

```yaml
output:
  status: success | partial | failed
  artifacts:
    - path: <产物路径>
      type: <产物类型>
      description: <产物描述>
  metadata:
    execution_time: <执行时间>
    skill_version: <Skill版本>
  errors: []
  warnings: []
```

#### 5.5.3 状态语义

| 状态 | 含义 | 下游行为 |
|------|------|---------|
| `success` | 目标已完成 | 继续下游 |
| `partial` | 产出不完整但可用 | 记录警告，继续下游 |
| `failed` | 无法继续 | 立即停止，保留 checkpoint |

### 5.6 Orchestration 类局部风格

**代表 Skill**: `pb-review`, `powerby-command`

#### 角色定位
流程编排者，负责协调多个 skill 完成复杂任务。

#### 判断重心
- 依赖管理：确保上游产物存在后再调用下游
- 状态管理：维护流程状态和 checkpoint
- 协议统一：所有子 skill 遵循统一输入/输出协议
- 错误处理：partial 状态记录警告并继续，failed 状态立即停止

#### 语气和输出形态
- **协调性**：清晰的流程步骤和依赖关系
- **透明性**：每个步骤的输入、输出、状态都可追溯
- **容错性**：支持断点恢复
- **聚合性**：将多个子 skill 的产出聚合为最终交付物

#### 禁止越界
- 不替代子 skill 的职责（只编排，不实现）
- 不跳过依赖直接调用下游

---

### 5.7 Bugfix 类局部风格

**代表 Skill**: `powerby-bugfix`

#### 角色定位
问题诊断者，负责快速准确地定位和修复问题。

#### 判断重心
- 证据驱动：所有推论必须基于日志、堆栈、代码逻辑
- 三层诊断：表现层 / 逻辑层 / 数据层独立诊断，再跨层验证
- 最小代价修复：在确保修复彻底的前提下，选择影响面最小的方案
- 需求对齐先于诊断：先确认"正确行为"的定义

#### 语气和输出形态
- **诊断性**：清晰的证据链和根因分析
- **方案性**：至少 2 个备选方案及其优缺点对比
- **验证性**：复现测试、回归测试、边界测试
- **闭环性**：单文档记录完整过程

#### 禁止越界
- 不做大规模重构（只修复问题，不改架构）
- 不做新功能开发（只修复 Bug，不增加功能）

---

### 5.8 Quick/Fullstack 类局部风格

**代表 Skill**: `powerby-fullstack`

#### 角色定位
全栈工程师，负责快速处理临时小需求。

#### 判断重心
- 速度来自精简范围：严格控制 P0 功能数量（≤5 个）和工作量（≤3 天）
- 增量扩展优于独立创建：在现有标准文档基础上增量扩展
- 三视角融合：产品理解 + 架构适配 + 工程规划在同一角色完成
- 质量不打折：文档质量与标准流程完全一致

#### 语气和输出形态
- **快速性**：全流程 ≤ 5 小时
- **融合性**：产品 + 架构 + 工程三视角在同一文档中体现
- **标准性**：遵循现有模板和规范
- **确认性**：计划确认是唯一的人工确认点

#### 禁止越界
- 不做 P6 开发实现（交给 engineer）
- 不做 P7-P8 代码审查和交付（交给 code-review）
- 工作量超过 3 天的需求建议转标准流程

## 6. 渐进升级路径

### 6.1 升级原则

1. **协议先行，文档先行**：先完成协议层和文档层升级，再逐个升级 Skill
2. **不破坏现有可用流程**：升级过程中，现有流程必须保持可用
3. **先核心后外围**：优先升级核心 Skill（product/architect/engineer/code-review）
4. **增量验证**：每个升级步骤完成后，通过实际项目验证效果
5. **向后兼容**：旧版本文档和 Skill 在升级期间保持可用

### 6.2 升级路径（分 4 个阶段）

#### 阶段 1：建立协议层（1-2 周）

**目标**：形成 PowerBy vNext 的协议体系和统一风格底座

**任务清单**：

- [ ] 编写 `docs/powerby-skill-protocol.md`（Skill 统一协议标准）

**验收标准**：
- 所有新文档已完成并通过团队评审
- 文档之间无冲突，逻辑自洽
- 与现有流程的映射关系清晰

**风险与缓解**：

## 7. 总结

### 7.1 核心成果

本设计方案（v2.0）完成了以下核心工作：

1. **建立了协议先行的升级策略**
   - 13 条核心协议（P-01 到 P-13）作为顶层指导
   - 3 层协议体系：顶层原则 → 阶段协议 → Skill 协议
   - 协议驱动的渐进升级路径

2. **以 ASP 流程为主要参考重新设计总流程**
   - Think → Plan → Build → Review → Test → Ship → Reflect 认知框架
   - ASP 7 阶段流程作为 Think 和 Plan 的标准实现
   - 标准流程、快速流程、Bugfix 流程统一映射到总循环

3. **引入自我改进循环（Retro-Learn）**
   - Retrospective → Learn → Update → Apply 四阶段循环
   - 项目级和组织级双层反馈机制
   - 持续优化流程和 Skill

4. **设计了三阶段执行协议**
   - Research → Plan (AI 自主批准) → Execute → Review Loop → Deliver
   - AI 自主决策与用户确认的平衡
   - Review Loop 确保质量和对齐

5. **建立了 Skill 统一协议标准**
   - 七层结构框架（新增 Philosophy and Principles 层）
   - 两层风格继承机制（powerby-foundation → 局部风格）
   - 统一输入/输出协议（编排链路）
   - 8 类 Skill 的局部风格定义

6. **形成了渐进升级路径**
   - 4 个阶段的升级计划（12 周）
   - 兼容性保障策略
   - 升级成功标准
   - 关键里程碑

---


### 7.2 关键特点

本设计方案（v2.0）的关键特点：

1. **协议先行，不是流程先行**
   - 13 条核心协议作为顶层指导
   - 3 层协议体系确保一致性
   - 协议驱动的渐进升级

2. **ASP 为主，不是 P0-P8 为主**
   - ASP 流程作为 Think 和 Plan 的标准实现
   - 标准流程映射到总循环
   - 快速流程和 Bugfix 流程统一到总循环

3. **自我改进，不是一次性设计**
   - Retro-Learn 循环内建
   - 项目级和组织级双层反馈
   - 持续优化流程和 Skill

4. **三阶段执行，不是单阶段执行**
   - Research → Plan → Execute → Review Loop → Deliver
   - AI 自主决策与用户确认的平衡
   - Review Loop 确保质量

5. **统一风格，不是各自为政**
   - 全局统一风格底座（powerby-foundation）
   - 局部 Skill 风格继承
   - 两层风格体系确保一致性

### 7.5 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| 协议层过于抽象，难以落地 | 高 | 中 | 每条协议都要有具体的落地方式和示例 |
| 与现有流程冲突 | 高 | 低 | 充分识别保留项清单，确保兼容 |
| 升级周期过长，影响团队士气 | 中 | 中 | 分批升级，及时反馈进展 |
| 文档和 Skill 不同步 | 中 | 中 | 建立文档和 Skill 的同步机制 |
| Skill 升级后行为变化导致用户困惑 | 中 | 高 | 提供迁移指南和示例 |
| 升级后性能下降 | 低 | 低 | 保持 Skill 精简，避免过度抽象 |
