## 1. PowerBy 当前流程现状总结

### 1.1 标准主流程 (P0-P8)

**流程骨架**:
```
P0 项目初始化 → P1 需求定义+澄清 → P3 技术调研 → P4 架构设计 → 
P5 任务规划 → P6 开发实现 → P7 代码审查 → P8 发布交付
```

**核心特征**:
- 9 个阶段，5 个质量门禁 (Gate 0/1/3/4/5)
- P2 已合并到 P1，采用"需求定稿制"融合澄清过程
- 分支创建时机：P1 完成后（Gate 1 通过）自动创建 feature 分支
- 文档驱动：每个阶段都有明确的输入文档、输出文档和验收标准
- 角色分工：Product Manager (P0-P1) → Architect (P3-P4) → Engineer (P5-P6) → Reviewer (P7)

**关键 Skills**:
- `powerby-product`: P0-P1 阶段，负责项目初始化和需求定义
- `powerby-architect`: P3-P4 阶段，负责技术调研和架构设计
- `powerby-engineer`: P5-P6 阶段，负责任务规划和开发实现
- `powerby-code-review`: P7 阶段，负责代码审查
- `powerby-reviewer`: 交付完成确认与证据链治理

### 1.2 快速流程 (P0-P5)

**流程骨架**:
```
P0+P1 需求定义+澄清(自动初始化) → P3 技术调研 → P4 架构设计 → 
P5 任务规划 → [创建feature分支] → 交付
```

**核心特征**:
- 适用场景：临时小需求（≤3天工作量）、增量开发
- 时间约束：全流程 ≤ 5 小时
- P0 功能点数量：≤ 5 个
- 分支创建时机：P5 完成后（Q-Gate 5 通过）
- 三视角融合：产品理解 + 架构适配 + 工程拆解在同一角色完成

**关键 Skill**:
- `powerby-fullstack`: P0-P5 快速流程的全栈工程师角色

### 1.3 Bug 修复流程

**流程骨架**:
```
问题报告 → 需求对齐 → 三层诊断 → 方案设计 → 实施修复 → 验证测试 → 交付归档
```

**核心特征**:
- 证据驱动的三层诊断：表现层 / 逻辑层 / 数据层
- 单文档闭环记录：从问题报告到验证通过全过程在一个文档中完成
- 分支策略：P0/P1 级别用 hotfix 分支，P2/P3 级别用 bugfix 分支
- 临时文件管理：`temp_scripts/` 目录在修复完成后必须清空

**关键 Skill**:
- `powerby-bugfix`: Bug 诊断与修复专项技能

### 1.4 ASP 独立流程

**流程骨架**:
```
OFFICE_HOURS → DISCOVERY → DRAFTING → DESIGNING → REFINING → VISUALIZING → CONFIRMATION
```

**核心特征**:
- 前置探讨先于合同锁定：先通过 OFFICE_HOURS 澄清，再通过 DISCOVERY 收敛为 proposal
- 分阶段组装：产品阶段负责 D-01~D-08 + D-17~D-20，架构阶段负责 D-09~D-16
- 测试化内建：每张规格卡必须内建 Test Oracle、Fixture Contract、Test Case Groups、Coverage Claim
- 双层事实源：design-brief.md (前置探讨) + proposal.md (需求边界) + feature-spec-index.md (Feature 索引) + architecture.md (架构设计)

**关键 Skills**:
- `powerby-asp-office-hours`: 前置产品设计与澄清
- `powerby-asp-product`: 产品经理角色，DISCOVERY + DRAFTING 阶段
- `powerby-asp-architect`: 架构师角色，DESIGNING 阶段
- `powerby-asp-reviewer`: 产品文档自动化审计
- `powerby-asp-arch-reviewer`: 架构文档自动化审计
- `powerby-asp-visualizer`: 产品全景图与测试化产物生成

### 1.5 分支管理与 Git 集成

**分支策略 (GitFlow)**:
- 主分支：`main` (生产) + `develop` (集成)
- 功能分支：`feature/{id}-{name}` (P0-P8 完整迭代)
- 修复分支：`bugfix/{id}-{desc}` (P2/P3) + `hotfix/{id}-{desc}` (P0/P1)

**自动化集成**:
- P1 完成后 → 自动创建 `feature/{id}-{name}` 分支（标准流程）
- P5 完成后 → 创建 `feature/{id}-{name}` 分支（快速流程）
- P8 完成后 → 自动合并分支到 `develop`
- Bug 修复时 → 自动选择 `bugfix/` 或 `hotfix/` 分支

**关键 Skills**:
- `powerby-git`: Git 分支管理专项技能，负责分支生命周期管理
- `powerby-github-branch`: GitHub 分支管理自动化

### 1.6 核心设计哲学与约束

**Px 执行协议**:
- 1+N 模式：进入阶段后第一个动作必须是定义子任务清单，然后逐一执行
- 增量执行：完成一个子任务标记一个，遇到阻塞记录并继续
- 贯穿始终：tasks.md 从 P1 阶段开始使用，持续追踪所有阶段进度

**迭代思维与复用优先**:
- 持续演进：项目是迭代演进的，不是一次性完成的
- 充分了解：在开始任何新工作之前，必须充分了解现有项目架构
- 严格遵循：识别并严格遵循项目已有的编码规范和最佳实践
- 优先复用：系统性识别可复用的现有服务、组件、工具类和业务逻辑
- 增量扩展：优先通过增量扩展现有能力来满足新需求

**质量门禁机制**:
- Gate 0: 项目可行性（P0 → P1）
- Gate 1: 需求定稿（P1 → P3，包括澄清）
- Gate 3: Constitution Gates（P4 → P5，Simplicity/Anti-Abstraction/Integration-First）
- Gate 4: 任务计划完整性（P5 → P6）
- Gate 5: 代码审查完整性（P7 → P8）

**变更控制**:
- 所有阶段必须记录变更并关联证据
- 记录位置：`docs/{project}/implementation/decisions.md`
- 最小变更记录字段：变更ID、变更类型、原因与影响范围、批准人、证据位置

### 1.8 Skill 设计协议

**七层结构框架**:
1. 触发层：frontmatter (name, description, compatibility)
2. 定位层：Purpose + Success criteria
3. 认知层：Strategy（设计哲学 + 判断框架）
4. 执行层：Tools and capability boundaries
5. 约束层：Important facts and constraints
6. 扩展层：Resources + Subtask guidance
7. 安全层：Safety

**渐进披露三层架构**:
- SKILL.md：高层策略与工作流（始终加载）
- references/：按需加载的领域知识
- scripts/：确定性/重复性操作
- assets/：模板文件

**统一输入/输出协议**（编排链路）:
```yaml
# 统一输入
context: <共享上下文对象>
parameters: <本次调用参数>

# 统一输出
status: success | partial | failed
objects: []          # 新发现的结构化记录
relations: []        # 新建立的关系
conflicts: []        # 新发现的冲突
gaps: []             # 新发现的缺口
context_writes: {}   # 写回哪些 registry
metadata: {}         # 执行元数据
errors: []           # 错误信息
```

## 2. 旧版本必须保留的机制清单

### 2.1 底座能力（必须保留）

| 机制 | 当前作用 | 保留理由 | 调整方式 |
|------|---------|---------|---------|
| **Px 执行协议** | 强制任务拆解优先，1+N 模式 | 防止"大爆炸"式开发，确保执行透明可追溯 | 保持不变，作为全局执行准则 |
| **质量门禁机制** | 5 个 Gate 控制阶段流转 | 确保每个阶段产出质量，防止带病推进 | 映射到新总循环的验证点 |
| **文档驱动开发** | 所有工作严格基于文档，文档是事实源 | 确保可追溯性，防止口头约定和隐性知识 | 保持不变，强化文档协议 |
| **分支生命周期管理** | GitFlow 分支策略 + 自动化创建/合并 | 确保代码隔离和合并规范 | 保持不变，继续由 powerby-git 管理 |
| **变更控制** | 所有变更必须记录并关联证据 | 防止需求漂移和实现偏离 | 保持不变，强化追溯链 |
| **迭代思维与复用优先** | 充分了解、严格遵循、优先复用 | 确保增量演进，避免重复造轮子 | 保持不变，融入新流程原则 |

### 2.2 重要措施（必须保留）

| 机制 | 当前作用 | 保留理由 | 调整方式 |
|------|---------|---------|---------|
| **MVP 聚焦** | P0 功能点数量控制（≤10 个标准流程，≤5 个快速流程） | 防止范围蔓延，确保核心价值聚焦 | 保持不变，作为产品阶段核心约束 |
| **Constitution Gates** | P4 阶段的 Simplicity/Anti-Abstraction/Integration-First 三大门禁 | 防止过度设计和不必要抽象 | 保持不变，作为架构阶段核心约束 |
| **测试化内建** | 每个 P0 功能至少 1 个单元测试 + 1 个集成/验收步骤 | 确保代码质量和可验证性 | 保持不变，强化测试规格设计 |
| **证据驱动诊断** | Bug 修复必须基于显式证据，不基于猜测 | 确保问题定位准确，避免盲目修复 | 保持不变，作为 bugfix 流程核心原则 |
| **单文档闭环** | Bug 修复全过程在一个文档中完成 | 确保诊断经验可复用 | 保持不变 |
| **临时文件清理** | temp_scripts/ 目录在修复完成后必须清空 | 防止临时文件污染代码库 | 保持不变 |

### 2.3 保护性约束（必须保留）

| 机制 | 当前作用 | 保留理由 | 调整方式 |
|------|---------|---------|---------|
| **职责边界** | 每个 skill 明确声明"不做什么" | 防止职责越界和角色混乱 | 保持不变，融入统一风格底座 |
| **前置条件校验** | 进入阶段前检查前置文档是否存在 | 防止跳步执行和依赖缺失 | 保持不变，作为阶段协议的一部分 |
| **受阻原则** | 同一问题最多尝试 3 次，然后停止并启动障碍解决协议 | 防止无效循环和资源浪费 | 保持不变，作为全局执行准则 |
| **小步提交** | 每次提交必须可编译且通过所有测试 | 确保代码库始终可工作 | 保持不变，作为工程阶段核心约束 |
| **契约先行** | 所有公共接口在入口处实施 Guard Clauses 校验 | 快速暴露问题，降低调试成本 | 保持不变，作为工程阶段核心约束 |

### 2.4 需要收敛的冲突或过时内容

| 问题 | 当前状态 | 收敛方式 |
|------|---------|---------|
| **标准流程 vs ASP 流程** | 两套独立流程，文档结构不同 | 统一到新总循环框架，ASP 作为"探讨性"阶段的标准实现 |

## 3. PowerBy vNext 顶层流程原则

### 3.1 总原则：三层本质

PowerBy vNext 的核心是表达软件开发的三层本质：

1. **Think = 探讨与开创性**
   - 用于探讨、澄清、挑战前提、形成想象与方向判断
   - 允许开创性思考，不应过早进入实现细节
   - 输出：方向共识、核心假设、验证目标

2. **Plan / Build = 基于约束的实现还原**
   - 探讨和澄清之后，产物必须转化为协议、约束、规格、架构、任务
   - 后续实现应以"还原已确认目标"为核心，不允许再次自由发散
   - 输出：可执行的规格、架构、代码

3. **Review / Test / Ship / Reflect = 验证完成的闭环**
   - 完成不是"代码写完"
   - 必须经过审查、验证、交付、复盘，形成证据化闭环
   - 输出：审查报告、测试证据、交付清单、经验总结

### 3.2 核心原则（继承并强化现有原则）

#### P-01 AI 自助优先
只要协议、约束和目标足够明确，AI 应尽可能自主完成任务。不确定或影响面巨大的决策，集中列出后交由用户统一裁决。

#### P-02 任务分级
- 确定性高、影响面小的事项由 AI 自主完成
- 不确定或影响面巨大的决策，集中列出后交由用户统一裁决

#### P-03 协议先行
先定义流程协议、阶段协议、文档协议、验证协议，再执行。所有角色在同一组协议上协同工作。

#### P-04 文档归档
标准流程中的关键产物必须具象化、可归档、可追踪、可复用。文档是事实源，不是事后补充。

#### P-05 借鉴之后创造
先找已有标准、最佳实践、现有代码、现有数据，再在其基础上改造优化。Search Before Building。

#### P-06 拥抱务实
不教条，不为了"理论完整"牺牲项目现实。选择能解决问题的最简单方案。

#### P-07 演进式架构
支持增量、引导式的架构变更，使其能适应未来的需求演化。基于现有架构的增量演进是默认路径。

#### P-08 测试即规格
"没有测试的代码就是不存在的代码"。所有功能必须由自动化测试来定义和验证。

#### P-09 证据驱动
所有推论必须基于显式证据（日志、堆栈、代码逻辑）。当证据不足时，设计实验获取新证据，而不是基于假设直接行动。

#### P-10 小步提交，持续可工作
每次提交必须可编译且通过所有测试。频繁的小步提交比大爆炸式开发更安全。

### 3.3 判断框架（Search Before Building）

参考 gstack 的判断框架，PowerBy vNext 采用三层判断优先级：

1. **Tried and True（已验证方案）**
   - 优先使用项目中已有的、经过验证的模式和组件
   - 复用现有技术栈和架构模式
   - 遵循项目已有的编码规范和最佳实践

2. **New and Popular（成熟方案）**
   - 当已有方案无法满足需求时，选择社区成熟、广泛使用的方案
   - 评估团队熟悉度和学习成本
   - 考虑长期维护和社区支持

3. **First Principles（第一性原理）**
   - 只有在前两者都无法满足需求时，才从第一性原理出发创新
   - 必须充分论证为何现有方案无法满足
   - 创新方案必须有清晰的设计文档和决策记录

### 3.4 质量标准（不因"快速"而打折）

无论是标准流程、快速流程还是 bugfix 流程，质量标准保持一致：

- **可测试性**：能轻松地测试这个方案吗？
- **可读性**：6 个月后，其他人能看懂这段代码吗？
- **一致性**：是否符合项目现有的模式？
- **简单性**：这是能解决问题的最简单的方案吗？
- **可逆性**：如果未来发现决策错误，修改它的成本有多高？

## 4. PowerBy 全局统一风格底座

### 4.1 底座目标

建立一套适用于所有 PowerBy skill 的统一规范，确保：
- 所有 skill 看起来属于同一个体系
- 用户跨 skill 使用时感受到统一的行为与表达
- 减少每个 skill 各自为政、风格漂移

### 4.2 全局设计哲学

所有 PowerBy skill 共同遵循的顶层哲学：

#### 4.2.1 零假设原则 (Zero-Assumption Principle)
绝不猜测用户的模糊意图。当指令不明确或缺少关键信息时，首要职责是提出具体问题以澄清需求，而不是基于假设进行工作。

#### 4.2.2 文档驱动 (Document-Driven)
所有工作严格基于文档。文档是事实源，不是事后补充。当文档之间存在冲突时，遵循明确的优先级规则。

#### 4.2.3 证据驱动 (Evidence-Driven)
所有推论必须基于显式证据。当证据不足时，设计实验获取新证据，而不是基于假设直接行动。

#### 4.2.4 增量演进 (Incremental Evolution)
优先通过增量扩展现有能力来满足新需求，而非创建孤立的实现。基于现有架构的增量演进是默认路径。

#### 4.2.5 务实权衡 (Pragmatic Trade-offs)
不存在银弹方案。核心价值在于清晰识别不同方案之间的利弊权衡，并给出基于证据的务实建议。

#### 4.2.6 最小影响面 (Minimize Impact)
在确保目标达成的前提下，选择影响面最小的方案。不改变系统架构，只在必要范围内修改。

### 4.3 统一协议结构

所有 PowerBy skill 的 SKILL.md 必须遵循七层结构框架：

```markdown
---
name: <skill-name>
description: |
  <核心能力 + 典型触发语境 + 不适用边界>

  - <兼容性声明>

<一段话说清能力和成功使用的样子>

## Strategy

<3-5 条核心设计原则>
```

### 4.4 统一表达风格

#### 4.4.1 文风要求
- **祈使句为主**：`Start by...`, `Choose the...`, `Treat each...`
- **解释原因**：不只说"做什么"，要说"为什么这样做"
- **少用 MUST/NEVER**：风险边界除外，正文用启发式写法
- **真实用户化示例**：Examples 像真实请求，不像教科书

#### 4.4.2 抽象层级
- SKILL.md 正文保持精简（不超过 200 行正文，不含示例）
- 大段领域知识放入 references/，按需加载
- 确定性操作下沉到 scripts/
- 模板文件放入 assets/

#### 4.4.3 禁止项
- 禁止在 SKILL.md 中堆砌大段示例代码
- 禁止使用模糊表述（"可能"、"也许"、"大概"）
- 禁止写死流程（写策略哲学，不写 click-by-click 细节）
- 禁止跨 skill 职责（明确边界，不越权）

### 4.5 统一确认与验证方式

#### 4.5.1 AI 自主执行的情况
- 协议、约束和目标足够明确
- 确定性高、影响面小
- 有明确的验收标准

#### 4.5.2 必须升级为用户决策的情况
- 存在多个合理方案，需要权衡
- 影响面巨大或不可逆
- 涉及业务方向或产品策略
- 技术选型有重大影响

#### 4.5.3 完成状态声明
所有 skill 必须明确声明三种状态：

- **success**：目标已完成，可继续下游
- **partial**：产出不完整但结果仍可用，记录警告并继续
- **failed**：无法继续，立即停止，保留 checkpoint

### 4.6 统一产物与归档观

#### 4.6.1 哪些输出必须落盘
- 所有阶段的核心交付物（PRD、架构、任务、代码、审查报告）
- 所有重要决策及其理由
- 所有变更记录及其证据

#### 4.6.2 哪些结论必须有证据
- 技术选型决策
- 架构设计决策
- Bug 根因分析
- 性能优化效果

#### 4.6.3 哪些阶段必须具象化文档
- 需求定义阶段：prd.md, function-points.md, clarifications.md
- 架构设计阶段：architecture.md, data-model.md, contracts/
- 开发实现阶段：tasks.md, implementation-report.md, decisions.md
- 代码审查阶段：code-review-report.md, acceptance-test.md

### 4.7 统一安全和边界表达

所有 skill 必须在 Safety section 显式声明禁止行为：

```markdown
## Safety
- 不允许跳过上游依赖直接调用下游 skill
- 不允许把推断结果写成显式事实
- 不允许修改不属于本 skill 职责范围的文档
- 不允许绕过质量门禁强行推进
- 不允许在证据不足时基于假设行动
```

## 5. 关键 Skill 类型的局部风格规范

### 5.1 Product 类 Skill 局部风格

**代表 Skill**: `powerby-product`, `powerby-asp-product`, `powerby-asp-office-hours`

#### 5.1.1 角色定位
产品经理视角，负责"定义做什么"，不侵入"如何做"。

#### 5.1.2 判断重心
- MVP 聚焦：每个功能都要问"去掉它用户还能否完成核心任务"
- 模糊即停：遇到信息不足立即生成澄清问题，不猜测
- 范围边界：显式定义 In-Scope / Out-of-Scope
- 优先级排序：P0/P1/P2 标记必须有明确理由

#### 5.1.3 语气和输出形态
- **探讨性**：允许开放式讨论，挑战前提，形成方向共识
- **收敛性**：最终必须收敛为明确的功能点清单和待决策清单
- **用户导向**：所有功能描述从用户视角出发，不涉及技术实现
- **决策透明**：每个决策点提供至少 2 个方案及其 MVP 角度的利弊分析

#### 5.1.4 禁止越界
- 不做技术选型（交给 architect）
- 不做架构设计（交给 architect）
- 不做代码实现（交给 engineer）
- 不定义实现细节（只定义 What，不定义 How）

---

### 5.2 Architect 类 Skill 局部风格

**代表 Skill**: `powerby-architect`, `powerby-asp-architect`

#### 5.2.1 角色定位
架构师视角，负责"设计如何做"，将需求转化为技术蓝图。

#### 5.2.2 判断重心
- 忠于需求：所有架构组件必须可追溯到 PRD 中的功能点
- 务实权衡：清晰识别不同方案的利弊，给出基于证据的建议
- 原子与编排分层：区分稳定的原子服务和可变的编排服务
- 契约先行：每个服务接口必须有精确的契约定义
- 增量演进：基于现有架构的增量演进是默认路径

#### 5.2.3 语气和输出形态
- **结构性**：清晰的架构图、组件定义、数据模型
- **权衡性**：每个关键决策点提供多方案对比和权衡分析
- **约束性**：明确技术约束、性能边界、安全要求
- **可追溯性**：组件与需求映射表、变更点说明、影响分析

#### 5.2.4 禁止越界
- 不修改 PRD 的功能定义（尊重产品视角）
- 不做代码实现（交给 engineer）
- 不做代码审查（交给 code-review）

---

### 5.3 Engineer 类 Skill 局部风格

**代表 Skill**: `powerby-engineer`

#### 5.3.1 角色定位
工程师视角，负责"实现如何做"，将架构转化为高质量代码。

#### 5.3.2 判断重心
- 文档驱动：所有工作严格基于 proposal.md、architecture.md、tasks.md
- 测试即规格：先写失败的测试定义期望行为，再写代码让测试通过
- 契约先行：所有公共接口在入口处实施 Guard Clauses 校验
- 小步提交：每次提交必须可编译且通过所有测试
- 复用优先：研究项目中的既有模式，严格遵循已有规范

#### 5.3.3 语气和输出形态
- **还原性**：基于已确认的架构和任务，不自由发散
- **验证性**：每个功能都有对应的测试用例
- **可追溯性**：任务 → 需求 → 架构组件 → 测试用例的完整链路
- **问题导向**：遇到障碍立即启动障碍解决协议，不绕过问题

#### 5.3.4 禁止越界
- 不修改 proposal.md 的功能定义（尊重产品视角）
- 不修改 architecture.md 的架构设计（尊重架构决策）
- 不做代码审查（交给 code-review）

---

### 5.4 Review / Reviewer 类 Skill 局部风格

**代表 Skill**: `powerby-code-review`, `powerby-reviewer`, `powerby-asp-reviewer`, `powerby-asp-arch-reviewer`

#### 5.4.1 角色定位
审查者视角，负责"验证是否做对"，确保质量和一致性。

#### 5.4.2 判断重心
- 证据驱动：所有审查结论必须基于显式证据
- 三向对齐：PRD ↔ 架构 ↔ 实现的一致性检查
- 边界检查：识别假实现、硬编码、TODO、空函数
- 风险识别：安全漏洞、性能瓶颈、技术债务
- DoD 量化：Definition of Done 的可量化验收

#### 5.4.3 语气和输出形态
- **审计性**：系统化的检查清单和审计报告
- **证据性**：每个问题都有具体的文件路径、行号、代码片段
- **风险性**：明确标注风险等级（高/中/低）和影响范围
- **建议性**：不只指出问题，还提供修复建议和优先级

#### 5.4.4 禁止越界
- 不修改代码（只审查，不实现）
- 不修改需求（只验证，不定义）
- 不修改架构（只检查，不设计）

---

### 5.5 Orchestration 类 Skill 局部风格

**代表 Skill**: `pb-review`, `powerby-command`

#### 5.5.1 角色定位
流程编排者视角，负责"协调多个 skill 完成复杂任务"。

#### 5.5.2 判断重心
- 依赖管理：确保上游产物存在后再调用下游 skill
- 状态管理：维护流程状态和 checkpoint，支持断点恢复
- 协议统一：所有子 skill 遵循统一的输入/输出协议
- 错误处理：partial 状态记录警告并继续，failed 状态立即停止

#### 5.5.3 语气和输出形态
- **协调性**：清晰的流程步骤和依赖关系
- **透明性**：每个步骤的输入、输出、状态都可追溯
- **容错性**：支持断点恢复，不因单点失败而全盘重来
- **聚合性**：将多个子 skill 的产出聚合为最终交付物

#### 5.5.4 禁止越界
- 不替代子 skill 的职责（只编排，不实现）
- 不跳过依赖直接调用下游（严格遵循依赖顺序）

---

### 5.6 Bugfix 类 Skill 局部风格

**代表 Skill**: `powerby-bugfix`

#### 5.6.1 角色定位
问题诊断者视角，负责"快速准确地定位和修复问题"。

#### 5.6.2 判断重心
- 证据驱动：所有推论必须基于日志、堆栈、代码逻辑
- 三层诊断：表现层 / 逻辑层 / 数据层独立诊断，再跨层验证
- 最小代价修复：在确保修复彻底的前提下，选择影响面最小的方案
- 需求对齐先于诊断：先确认"正确行为"的定义，再判断是否偏离

#### 5.6.3 语气和输出形态
- **诊断性**：清晰的证据链和根因分析
- **方案性**：至少 2 个备选方案及其优缺点对比
- **验证性**：复现测试、回归测试、边界测试
- **闭环性**：单文档记录完整过程，形成可复用的诊断经验

#### 5.6.4 禁止越界
- 不做大规模重构（只修复问题，不改架构）
- 不做新功能开发（只修复 Bug，不增加功能）

### 5.7 Quick/Fullstack 类 Skill 局部风格

**代表 Skill**: `powerby-fullstack`

#### 5.7.1 角色定位
全栈工程师视角，负责"快速处理临时小需求"。

#### 5.7.2 判断重心
- 速度来自精简范围：严格控制 P0 功能数量（≤5 个）和工作量（≤3 天）
- 增量扩展优于独立创建：在现有标准文档基础上增量扩展
- 三视角融合：产品理解 + 架构适配 + 工程规划在同一角色完成
- 质量不打折：文档质量与标准流程完全一致

#### 5.7.3 语气和输出形态
- **快速性**：全流程 ≤ 5 小时
- **融合性**：产品 + 架构 + 工程三视角在同一文档中体现
- **标准性**：遵循现有模板和规范，不创建新格式
- **确认性**：计划确认是唯一的人工确认点

#### 5.7.4 禁止越界
- 不做 P6 开发实现（交给 engineer）
- 不做 P7-P8 代码审查和交付（交给 code-review）
- 工作量超过 3 天的需求建议转标准流程

## 6. Think → Plan → Build → Review → Test → Ship → Reflect 总流程设计

### 6.1 总循环概述

PowerBy vNext 采用 **Think → Plan → Build → Review → Test → Ship → Reflect** 作为顶层认知框架，表达软件开发的完整循环。

**重要说明**：
- 这个循环是**认知框架**，不是对现有 P0-P8 的替换
- 它是对现有流程的**更高层抽象**，帮助理解每个阶段的本质
- 现有 P0-P8 阶段映射到这个循环的不同节点
- 快速流程、bugfix 流程、ASP 流程都可以映射到这个循环

### 6.2 循环节点定义

#### 6.2.1 Think（探讨与开创）

**本质**：探讨、澄清、挑战前提、形成想象与方向判断

**特征**：
- 允许开创性思考，不应过早进入实现细节
- 可以质疑需求、挑战假设、探索可能性
- 输出是方向共识、核心假设、验证目标

**映射到现有流程**：
- 标准流程：P0 项目初始化（部分）、P1 需求定义的前期探讨
- ASP 流程：OFFICE_HOURS 阶段
- 快速流程：P0 快速初始化的可行性评估

**关键产物**：
- design-brief.md（ASP 流程）
- 项目宪章的核心理念部分
- 需求原始输入和初步想法

---

#### 6.2.2 Plan（规划与约束）

**本质**：将探讨结论转化为协议、约束、规格、架构

**特征**：
- 探讨结束后，必须收敛为明确的规格和约束
- 不再允许自由发散，所有决策基于已确认的方向
- 输出是可执行的规格、架构蓝图、任务清单

**映射到现有流程**：
- 标准流程：P1 需求定义（收敛部分）、P3 技术调研、P4 架构设计、P5 任务规划
- ASP 流程：DISCOVERY、DRAFTING、DESIGNING 阶段
- 快速流程：P1 需求定稿、P3 技术快速调研、P4 架构快速设计、P5 任务快速规划

**关键产物**：
- prd.md, function-points.md（需求规格）
- proposal.md, feature-spec-index.md, feature-specs/*.md（ASP 规格）
- technical-research.md（技术选型）
- architecture.md（架构蓝图）
- tasks.md（任务清单）

---

#### 6.2.3 Build（实现与还原）

**本质**：基于已确认的规格和架构，还原为高质量代码

**特征**：
- 严格基于文档驱动，不自由发散
- 以"还原已确认目标"为核心
- 测试即规格，先写测试再写代码

**映射到现有流程**：
- 标准流程：P6 开发实现
- 快速流程：P6 开发实现（由 powerby-engineer 接手）
- Bugfix 流程：实施修复阶段

**关键产物**：
- 源代码
- 单元测试、集成测试
- implementation-report.md
- decisions.md（实现决策记录）

---

#### 6.2.4 Review（审查与验证）

**本质**：验证实现是否符合规格和架构

**特征**：
- 证据驱动的审查，不基于主观判断
- 三向对齐：PRD ↔ 架构 ↔ 实现
- 识别假实现、技术债务、安全漏洞

**映射到现有流程**：
- 标准流程：P7 代码审查
- ASP 流程：REFINING 阶段（产品文档审查）、REVIEWING 阶段（架构文档审查）
- Bugfix 流程：方案设计阶段的方案评审

**关键产物**：
- code-review-report.md
- prd_logs/round-{N}-{reviewer}.md（ASP 产品审查）
- arch_logs/round-{N}-{reviewer}.md（ASP 架构审查）

---

#### 6.2.5 Test（测试与质量保证）

**本质**：通过自动化测试验证功能正确性

**特征**：
- 测试即规格，测试定义了"正确"的标准
- 覆盖单元测试、集成测试、验收测试
- 测试通过是质量门禁的必要条件

**映射到现有流程**：
- 标准流程：P6 开发实现中的测试编写、P7 代码审查中的测试验证
- ASP 流程：feature-specs/*.md 中的 D-17~D-20 测试维度
- Bugfix 流程：验证测试阶段（复现测试、回归测试、边界测试）

**关键产物**：
- 测试代码（单元测试、集成测试、E2E 测试）
- checklists/testing.md（测试验收清单）
- testability-scorecard.md（ASP 测试化评分）
- acceptance-test.md（验收测试报告）

---

#### 6.2.6 Ship（交付与发布）

**本质**：将验证通过的代码交付到生产环境

**特征**：
- 部署到生产环境
- 生成 Release Notes
- 配置监控和告警

**映射到现有流程**：
- 标准流程：P8 发布交付
- 快速流程：交付阶段（简化版）
- Bugfix 流程：交付归档阶段

**关键产物**：
- Release Notes
- deployment-guide.md
- 生产环境部署记录

---

#### 6.2.7 Reflect（复盘与改进）

**特征**：

### 6.3 循环特性

#### 6.3.1 非线性循环
总循环不是严格线性的，可以根据实际情况调整：
- Think 阶段发现方向不对，可以重新 Think
- Plan 阶段发现技术不可行，可以回到 Think 重新探讨
- Review 阶段发现重大问题，可以回到 Plan 或 Build
- Test 阶段发现设计缺陷，可以回到 Plan

#### 6.3.2 快速流程的循环压缩
快速流程通过压缩循环节点来提速：
- Think + Plan 融合：可行性评估 + 需求定稿 + 架构设计在 5 小时内完成
- Build 外包：交给 powerby-engineer
- Review + Test + Ship 简化：快速验证后交付

#### 6.3.3 Bugfix 流程的循环变体
Bugfix 流程是循环的特殊变体：
- Think = 问题报告 + 需求对齐
- Plan = 三层诊断 + 方案设计
- Build = 实施修复
- Review + Test = 验证测试
- Ship = 交付归档
- Reflect = 经验记录

## 8. 阶段协议定义

### 8.1 Think 阶段协议

#### 输入
- 用户的产品想法或问题描述
- 现有项目的背景信息（如果是增量需求）

#### 输出
- 方向共识文档（design-brief.md 或需求原始输入）
- 核心假设清单
- 验证目标

#### 文档产物
- `design-brief.md`（ASP 流程）
- `docs/constitution.md`（项目宪章的核心理念部分）
- `prd.md` 的需求原始输入部分

#### 确认点
- 用户确认方向是否正确
- 核心假设是否合理
- 验证目标是否明确

#### 验证方式
- 用户反馈确认
- 与现有项目目标的一致性检查

---

### 8.2 Plan 阶段协议

#### 输入
- Think 阶段的方向共识
- 现有项目的架构和代码（如果是增量需求）

#### 输出
- 需求规格文档（prd.md, function-points.md）
- 技术调研报告（technical-research.md）
- 架构设计文档（architecture.md）
- 任务清单（tasks.md）

#### 文档产物
- `prd.md`, `function-points.md`, `clarifications.md`
- `proposal.md`, `feature-spec-index.md`, `feature-specs/*.md`（ASP）
- `technical-research.md`
- `architecture.md`, `data-model.md`, `contracts/`
- `tasks.md`

#### 确认点
- Gate 1: MVP 需求定稿检查
- Gate 3: Constitution Gates（Simplicity/Anti-Abstraction/Integration-First）
- Gate 4: 任务计划完整性

#### 验证方式
- 质量门禁检查清单
- 文档完整性验证
- 可追溯性检查（需求 → 架构 → 任务）

---

### 8.3 Build 阶段协议

#### 输入
- Plan 阶段的所有文档（prd.md, architecture.md, tasks.md）
- 现有代码库和测试框架

#### 输出
- 源代码
- 单元测试、集成测试
- 实现报告（implementation-report.md）
- 实现决策记录（decisions.md）

#### 文档产物
- 源代码文件
- 测试代码文件
- `implementation-report.md`
- `decisions.md`
- `work-log.md`

#### 确认点
- 所有 P0 任务已完成
- 测试覆盖率达标（≥80%）
- 代码质量符合项目标准

#### 验证方式
- tasks.md 中所有任务已标记完成 [x]
- 自动化测试通过
- 代码 lint 检查通过
- checklists/ 中的验收清单已更新

---

### 8.4 Review 阶段协议

#### 输入
- Build 阶段的所有产物（代码、测试、文档）
- Plan 阶段的所有文档（作为审查基准）

#### 输出
- 代码审查报告（code-review-report.md）
- 问题清单和修复建议
- 审查结论（APPROVED / CHANGES REQUESTED）

#### 文档产物
- `code-review-report.md`
- `prd_logs/round-{N}-{reviewer}.md`（ASP 产品审查）
- `arch_logs/round-{N}-{reviewer}.md`（ASP 架构审查）

#### 确认点
- Gate 5: 代码审查完整性
- 所有 Critical 问题已修复
- 三向对齐验证通过（PRD ↔ 架构 ↔ 实现）

#### 验证方式
- 5 大类审计清单
- 安全基线检查（高危=0，中危≤2）
- 证据索引可追溯性检查

---

### 8.5 Test 阶段协议

#### 输入
- Build 阶段的代码和测试
- Plan 阶段的测试规格（checklists/testing.md）

#### 输出
- 测试执行报告
- 测试覆盖率报告
- 验收测试结果（acceptance-test.md）

#### 文档产物
- `acceptance-test.md`
- `testability-scorecard.md`（ASP）
- 测试覆盖率报告

#### 确认点
- 单元测试覆盖率 ≥ 80%
- 集成测试通过率 ≥ 60%
- 所有 P0 功能的验收测试通过

#### 验证方式
- 自动化测试执行
- 测试覆盖率工具检查
- 手动验收测试

---

### 8.6 Ship 阶段协议

#### 输入
- Review 和 Test 阶段通过的代码
- 部署配置和脚本

#### 输出
- Release Notes
- 部署指南（deployment-guide.md）
- 生产环境部署记录

#### 文档产物
- `releases/v{version}-release-notes.md`
- `releases/deployment-guide.md`
- 生产环境部署日志

#### 确认点
- 生产环境部署成功
- 监控和告警已配置
- 用户文档已更新

#### 验证方式
- 部署脚本执行成功
- 生产环境健康检查通过
- 监控指标正常

---

### 8.7 Reflect 阶段协议

#### 输入
- 整个项目的所有文档和记录
- 团队成员的反馈

#### 输出
- 项目总结报告（project-retrospective.md）
- 流程改进建议
- 更新后的规范和模板

#### 文档产物
- `project-retrospective.md`
- 更新后的 `constitution.md`
- 流程改进文档

#### 确认点
- 项目统计数据已记录
- 做得好的地方已识别
- 改进建议已提出

#### 验证方式
- 团队回顾会议
- 文档归档检查

### 11.3 升级过程中的兼容性保障

#### 11.3.1 向后兼容策略

#### 11.3.2 迁移路径

#### 11.3.3 回滚机制
- 如果升级后发现重大问题，可以回滚到旧版本
- 保留旧版本文档和 Skill 的备份
- 建立问题反馈和快速修复机制

## 12. 总结

### 12.1 核心成果

本设计方案完成了以下核心工作：

1. **全面梳理了 PowerBy 当前流程现状**
   - 标准主流程（P0-P8）
   - 快速流程（P0-P5）
   - Bug 修复流程
   - ASP 独立流程
   - 分支管理与 Git 集成

2. **识别了必须保留的底座机制**
   - 底座能力：Px 执行协议、质量门禁、文档驱动、分支管理、变更控制、迭代思维
   - 重要措施：MVP 聚焦、Constitution Gates、测试化内建、证据驱动诊断
   - 保护性约束：职责边界、前置条件校验、受阻原则、小步提交、契约先行

3. **提炼了 PowerBy vNext 顶层原则**
   - 三层本质：Think（探讨与开创）、Plan/Build（基于约束的实现还原）、Review/Test/Ship/Reflect（验证完成的闭环）
   - 10 条核心原则：AI 自助优先、任务分级、协议先行、文档归档、借鉴之后创造、拥抱务实、演进式架构、测试即规格、证据驱动、小步提交
   - Search Before Building 判断框架：Tried and True → New and Popular → First Principles

4. **设计了全局统一风格底座**
   - 全局设计哲学：零假设原则、文档驱动、证据驱动、增量演进、务实权衡、最小影响面
   - 统一协议结构：七层结构框架
   - 统一表达风格：祈使句为主、解释原因、少用 MUST/NEVER
   - 统一确认与验证方式：AI 自主执行 vs 用户决策
   - 统一产物与归档观：哪些输出必须落盘、哪些结论必须有证据

5. **定义了关键 Skill 类型的局部风格**
   - Product 类：探讨性、收敛性、用户导向、决策透明
   - Architect 类：结构性、权衡性、约束性、可追溯性
   - Engineer 类：还原性、验证性、可追溯性、问题导向
   - Review/Reviewer 类：审计性、证据性、风险性、建议性
   - Orchestration 类：协调性、透明性、容错性、聚合性
   - Bugfix 类：诊断性、方案性、验证性、闭环性
   - Quick/Fullstack 类：快速性、融合性、标准性、确认性

6. **设计了 Think → Plan → Build → Review → Test → Ship → Reflect 总流程**
   - 作为认知框架，不是对现有 P0-P8 的替换
   - 是对现有流程的更高层抽象
   - 所有现有流程都可以映射到这个循环

7. **建立了完整的阶段职责矩阵和协议定义**
   - 总循环节点与现有阶段映射
   - Skill 与循环节点映射
   - 每个阶段的输入/输出/文档产物/确认点/验证方式

8. **明确了新旧流程映射关系**
   - 标准流程映射
   - ASP 流程映射
   - 快速流程映射
   - Bugfix 流程映射

9. **形成了新版本流程文档清单**
   - 5 个核心流程文档（新增）
   - 4 个现有流程文档（修订）
   - 所有 Skill 文档（逐个升级）

10. **给出了渐进升级实施建议**
    - 4 个阶段的升级路径
    - 兼容性保障策略
    - 升级成功标准
    - 关键里程碑

### 12.2 关键特点

本设计方案的关键特点：

1. **渐进式升级，不是推倒重来**
   - 基于现有 PowerBy 底座，保留所有有效机制
   - 参考 gstack 优秀实践，但不照搬
   - 升级路径清晰，风险可控

2. **统一风格体系，不是各自为政**
   - 全局统一风格底座，确保所有 Skill 属于同一体系
   - 局部 Skill 风格，保持角色辨识度
   - 风格继承关系清晰，避免风格漂移

3. **认知框架清晰，不是流程替换**
   - Think → Plan → Build → Review → Test → Ship → Reflect 是认知框架
   - 不替换现有 P0-P8，而是更高层抽象
   - 帮助理解每个阶段的本质

4. **三层本质表达，不是抽象口号**
   - Think = 探讨与开创性
   - Plan/Build = 基于约束的实现还原
   - Review/Test/Ship/Reflect = 验证完成的闭环
   - 每层都有明确的输入、输出、验证方式

5. **原则可落地，不是空洞理论**
   - 每条原则都能落到阶段职责、文档协议或验证机制上
   - 判断框架具体可操作（Search Before Building）
   - 质量标准明确可量化
