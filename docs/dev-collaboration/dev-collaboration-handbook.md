# 研发协作手册

> 这是完整的研发流程参考。日常只需遵守 3-Gate 卡，遇到问题时查阅对应章节。

---

## 第一章：搞清楚要做什么

**目标**：把模糊的需求变成边界清晰的范围定义，让所有人对"做什么、不做什么"达成共识。

**产出物**：
- 需求范围文档（scope.md）
- 关键流程走查（参照物截图串联 或 ASCII 草图）

### 怎么做

1. **先找参照物**：在现有产品、竞品、内部系统中找到和目标最接近的东西。截图，标注"我们要做的和它哪里一样、哪里不同"。找不到合适参照物时，用 ASCII 草图画出核心页面和流程。

2. **串联关键流程**：把 P0 功能的用户操作路径从头到尾串起来。不是罗列功能点，是让人能"走一遍"——用户从哪进来、每一步看到什么、做什么操作、最终到哪。

3. **做 MVP 分解**：
   - P0（必须做）：去掉它核心任务就无法完成
   - P1（重要可后排）：当前迭代做但不影响核心链路
   - P2（可选）：记录但当前不做
   - 判断标准：每个功能问自己"去掉它，用户还能完成核心任务吗？"

4. **列出疑问**：不确定的地方全部列出来。不确定时问，不要猜。用假设替代澄清是最常见的返工原因。

### 自检清单

- [ ] P0 功能的核心流程有走查（参照物或草图），能从头走到尾
- [ ] 每个 P0 功能能回答"去掉它核心任务是否失败"
- [ ] "不做什么"已明确列出
- [ ] 所有不确定的地方都列在疑问清单里，没有脑补

### 常见错误

- 把"用户想要的"当成"用户需要的"，功能越加越多
- 需求文档写了一堆文字但没有可视化流程，看完还是不知道产品长什么样
- P0 太多，什么都是最高优先级等于没有优先级

## 第二章：想清楚怎么做

**目标**：确定技术方案和关键架构决策，让"怎么实现"有明确路径。

**产出物**：
- 技术方案文档（方案对比 + 推荐）

### 怎么做

1. **先看现有代码**：任何方案的起点是"现在已经有什么"。能复用的复用，能扩展的扩展，别从零开始。

2. **至少给 2 个方案**：每个方案说清楚怎么做、优点、缺点。只有 1 个方案的"选择"不是决策。

3. **给出你的推荐**：明确说你推荐哪个方案、为什么。老板要的是你的专业判断，不是把选择题丢回来。

4. **识别关键决策**：影响全局的决策（技术选型、数据库选择、第三方服务）单独列出来。这些必须在写代码之前确认，写完再改成本最高。

### 自检清单

- [ ] 研究了现有代码中的相关实现，方案基于现状而非白纸
- [ ] 至少 2 种方案，每种有优缺点分析
- [ ] 有明确的推荐方案和推荐理由
- [ ] 关键决策已识别并列出，没有留到实现阶段再定

### 常见错误

- 没看现有代码就设计方案，做出来和现有系统风格不一致
- 只给一个方案让老板"确认"，实际上老板没有选择空间
- 关键决策没提前沟通，写到一半才发现方向不对

## 第三章：拆清楚怎么干

**目标**：把方案拆成可执行的任务，每个任务有明确的完成标准。

**产出物**：
- 任务清单（tasks.md）

### 怎么做

1. **按功能拆任务**：每个任务对应一个可独立验证的功能单元。粒度标准：一个人 1-2 天能完成，且有明确的"做到什么程度算完"。

2. **写验收标准**：每个任务必须有具体的验收标准。"登录功能完成"不是验收标准，"输入正确账号密码返回 token 并跳转首页，输入错误密码提示错误信息"才是。

3. **标注依赖关系**：哪些任务可以并行，哪些必须先后执行。识别关键路径——最长的那条依赖链决定了总工期。

4. **标注优先级**：P0 任务先做，P1 其次。P0 任务必须包含异常路径的处理，不只是正常流程。

### 自检清单

- [ ] 每个任务 1-2 天可完成，粒度合适
- [ ] 每个任务有具体的验收标准，不是"完成 XX 功能"
- [ ] 依赖关系已标注，关键路径已识别
- [ ] P0 任务包含异常路径处理

### 常见错误

- 任务拆得太粗（"实现后端"），执行时不知道从哪开始
- 验收标准模糊，做完了自己都不确定算不算完
- 没考虑依赖关系，并行开发时互相卡住

## 第四章：写代码

**目标**：按计划实现，每次提交都是可工作的状态。

### 怎么做

1. **先研究现有模式**：写代码前先看项目里类似功能是怎么实现的。找 3 个类似的实现参考，保持风格一致。

2. **小步提交**：每次提交都能编译、能运行。不要攒一大堆改动一次性提交。提交信息说明"为什么改"，不是"改了什么"。

3. **先写测试再写实现**（推荐）：先写一个会失败的测试定义"正确是什么样"，再写代码让它通过。这样你随时知道自己做到哪了。

4. **只做计划内的事**：每行代码都应该追溯到任务清单。发现"顺手可以改"的东西，记下来，但不在这次改。范围蔓延是最常见的延期原因。

5. **卡住了怎么办**：同一个问题最多试 3 次。第 4 次不是坚持，是固执。停下来，记录你试了什么、错误信息是什么、你觉得原因是什么，然后换个思路或者找人帮忙。

### 自检清单

- [ ] 研究了 3 个类似的现有实现，代码风格一致
- [ ] 每次提交可编译、可运行
- [ ] 没有做计划外的事情
- [ ] 卡住的问题没有死磕超过 3 次

### 常见错误

- 不看现有代码直接写，风格和项目格格不入
- 攒了一周的代码一次性提交，出问题无法定位
- "顺手"改了计划外的东西，引入新 bug
- 一个问题死磕半天不换思路

## 第五章：自己验

**目标**：交付前自己验证质量，不把明显的问题留给老板发现。

### 怎么做

1. **对照范围逐项检查**：拿出 Gate 1 确认的范围文档，P0 功能逐个过一遍。每个功能亲自操作一次，不是看代码觉得"应该没问题"。

2. **测正常流程**：核心用户路径从头走到尾，确保流程通畅。

3. **测异常流程**：输入错误数据、网络断开、权限不足——这些情况下系统不能崩溃，至少要有合理的错误提示。

4. **写自检报告**：逐项记录每个 P0 功能的验证结果。通过的标"通过"，有问题的标"问题 + 原因 + 是否已修复"。

### 自检清单

- [ ] P0 功能逐个亲自操作验证过，不是"看代码觉得没问题"
- [ ] 核心用户流程从头到尾走通
- [ ] 异常情况测过（错误输入、边界条件），系统不崩溃
- [ ] 自检报告已写，每个 P0 功能有明确的通过/未通过状态

### 常见错误

- 只在开发环境测，没有模拟真实使用场景
- 只测了正常流程，异常路径一个没试
- "我看代码没问题"代替实际测试
- 发现问题修了但没回归测试，修一个坏一个

---

## 第六章：交付

**目标**：确保交付物完整、可追溯、可回退。

### 怎么做

1. **交付前检查**：代码在正确的分支上、所有测试通过、没有未提交的改动。

2. **写变更说明**：这次交付改了什么、新增了什么、影响了什么。面向人写，不是复制 git log。重点标注破坏性变更（接口变了、配置变了、数据库变了）。

3. **演示给老板看**：跑起来，走一遍核心流程。能演示的问题比文字描述的问题发现率高 10 倍。

4. **合并代码**：确认无误后合并到主干。不用 force merge，有冲突先解决冲突。

### 自检清单

- [ ] 所有测试通过
- [ ] 变更说明已写，破坏性变更已标注
- [ ] 能跑起来演示核心流程
- [ ] 代码已合并，无冲突

### 常见错误

- 没写变更说明，别人不知道这次改了什么
- 破坏性变更没标注，下游系统被影响
- force merge 覆盖了别人的代码
- 交付后才发现本地能跑线上跑不了

## 附录：决策优先级

当多个方案都合理时，按这个顺序选：

1. **可测试** — 我能验证这个方案是对的吗？
2. **可读** — 6 个月后别人能看懂吗？
3. **一致** — 和项目现有风格一致吗？
4. **简单** — 这是最简单的方案吗？
5. **可逆** — 选错了改回来成本高吗？

## 附录：受阻处理

同一个问题试了 3 次还没解决：

1. **记录**：试了什么、错误信息、你觉得原因是什么
2. **研究**：找 2-3 个类似问题的解决方案
3. **反思**：是不是思路本身就不对？能不能换个更简单的方法？
4. **求助**：带着以上记录找人帮忙，不是空手问"这个怎么搞"
